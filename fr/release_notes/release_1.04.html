Version 1.4#

DataLab Version 1.4.0#

Prérequis#

  • DataLab-Platform :

    • Sigima 1.4.0 ou ultérieur est requis : il fournit les contrats d’opération et la qualification de rejeu, l’import d’images RAW, l’export d’images adapté au format, les annotations portables, les métadonnées d’origine expérimentale, la sérialisation d’objets au format NPZ et les règles de sélection par centre de pixel des ROI.

    • SigimaX 1.1.0 ou ultérieur est requis : il fournit les adaptateurs d’annotations PlotPy portables, les styles de courbes à contraste élevé, le rendu haute résolution de l’écran de démarrage et du filigrane, ainsi que l’exploration HDF5 NeXus et multidimensionnelle.

    • DataLab-Capsule 0.2.x (>= 0.2.0, < 0.3) est requis pour l’enregistrement et la vérification de la provenance des espaces de travail ainsi que l’échange de fichiers .dlcapsule.

  • PlotPyStack :

    • guidata 3.17.2 ou ultérieur est requis : il fournit les éléments de plage à histogramme, la priorité des icônes qualifiées par module, les fonctions d’images haute résolution, et donne à chaque fenêtre une barre de titre suivant le thème de couleurs sous Windows, y compris aux fenêtres des plugins (corrige Issue #492).

    • PlotPy 2.12.1 ou ultérieur est requis : il fournit des icônes SVG nettes sur les écrans haute résolution, le sous-échantillonnage automatique min/max des signaux et des interactions plus fluides sur les superpositions d’images.

  • Bibliothèques tierces :

    • Le package Python et les nouveaux projets de plugins générés exigent désormais Python 3.10 ou ultérieur. Les utilisateurs de Python 3.9 doivent conserver une version antérieure compatible. L’application autonome continue d’inclure son propre interpréteur Python.

    • Le lanceur de tests Windows exclut Python 3.9 des matrices courantes, tout en conservant les tests explicites de versions historiques précisément sélectionnées.

    • pip 22.2 ou ultérieur est requis pour résoudre et installer les dépendances additionnelles des plugins sous forme de wheels.

    • NumPy jusqu’à la version 2.5 (>= 1.22, < 2.6) et SciPy jusqu’à la version 1.18 (>= 1.10.1, < 1.19) sont désormais pris en charge.

✨ Nouvelles fonctionnalités#

Page d’accueil :

  • Une nouvelle page d”Accueil, semblable à celle de DataLab-Web, est affichée au démarrage et chaque fois que le panneau signal ou image courant est vide. Elle rassemble les principales actions pour bien démarrer : créer un signal ou une image, ouvrir des fichiers, parcourir un fichier HDF5, ouvrir un espace de travail HDF5, importer des données texte, interroger l’assistant IA, suivre la visite guidée, lancer la démo, lire la documentation ou consulter les notes de version

  • La page est un panneau ancrable, en onglet avec les vues signal et image : elle reste disponible après la création ou l’ouverture de données, et peut être rouverte à tout moment depuis le menu ? (Page d’accueil) ou depuis le menu Affichage

  • Une option Afficher la page d’accueil lorsque le panneau courant est vide, disponible sur la page elle-même et dans les paramètres généraux, détermine si la page est affichée automatiquement, y compris au démarrage

Luminosité et contraste :

  • Une nouvelle opération Traitement > Exposition > Luminosité et contraste fournit un histogramme avec des contrôles synchronisés du minimum, du maximum, de la luminosité et du contraste, des actions Auto et Réinitialiser déterministes, un remappage tenant compte des ROI et un aperçu interactif. Une plage d’entrée est initialisée à partir de la première image sélectionnée et appliquée à toute la sélection, chaque résultat conservant son image source et son type de données.

  • La fenêtre d’intensité peut s’étendre au-delà de la plage de données observée. Les limites en virgule flottante exactes survivent à l’édition et à la réapplication, tandis que les contraintes de paramètres déclarées restent appliquées et Annuler préserve les paramètres d’origine.

Import d’images RAW :

  • Les fichiers d’images RAW sans en-tête (*.raw) peuvent désormais être ouverts depuis Fichier > Ouvrir…, Fichier > Ouvrir depuis un répertoire…, par glisser-déposer, avec l’Assistant IA (outil load_file) et par contrôle à distance (load_from_files et load_from_directory avec un argument optionnel RawImageImportParam) (implémente l’issue #237)

  • La boîte de dialogue Import d’image RAW définit le type de données des pixels, la largeur et la hauteur de l’image, le décalage en octets avant la première image, le nombre d’images, l’espacement en octets entre images consécutives, l’ordre des octets, ainsi que l’option Blanc à zéro (qui affiche l’image importée avec une palette de niveaux de gris inversée sans modifier les valeurs des pixels). Les fichiers RAW multi-images créent une image par trame

  • Lorsque plusieurs fichiers RAW sont importés simultanément, DataLab demande s’il faut appliquer les mêmes paramètres d’import à tous les fichiers ou définir les paramètres de chaque fichier (chaque boîte de dialogue reprenant les valeurs validées pour le fichier précédent) ; les actions enregistrées dans l’historique conservent les paramètres d’import afin que leur rejeu ne rouvre pas la boîte de dialogue

Export d’images adapté au format :

  • L’enregistrement d’une image avec Fichier > Enregistrer… ouvre désormais une boîte de dialogue Exporter l’image adaptée au format de fichier sélectionné, avec un aperçu en direct affichant l’image en niveaux de gris telle qu’elle sera relue depuis le fichier exporté (y compris la quantification et la compression avec perte pour les fichiers BMP, PNG, JPEG, JPEG 2000 et TIFF) (implémente l’issue #256)

  • La préparation des données couvre la normalisation (aucune, min-max, percentiles ou bornes manuelles), le comportement hors plage (écrêtage ou rééchelonnage), le traitement des valeurs non finies (erreur, écrêtage ou remplacement), la correction gamma, l’inversion et la conversion vers un type de données pris en charge par le format de destination ; lors de l’export d’une image flottante ou d’un type non pris en charge vers un format uniquement entier (comme PNG, JPEG ou BMP), le rééchelonnage min-max est sélectionné par défaut, et les images complexes sont refusées lorsque le format ne peut pas stocker de valeurs complexes

  • Les options propres au format sont proposées et validées pour chaque format (niveau de compression PNG, qualité/sous-échantillonnage/progressif/optimisation/lissage JPEG, mode et couches de qualité/irréversible/ordre de progression/résolutions/tuilage/marqueurs PLT JPEG 2000, compression/niveau/prédicteur/lignes par bande/tuilage/résolution/interprétation photométrique TIFF, séparateur et précision des fichiers texte et CSV, compression MAT-File), et les actions enregistrées dans l’historique conservent les paramètres d’export ainsi que les UUID des objets cibles

Aperçu interactif des traitements :

  • Les boîtes de dialogue des traitements 1-vers-1 compatibles proposent désormais un aperçu interactif facultatif pour les signaux et images, y compris les opérations image-vers-signal. L’aperçu est désactivé par défaut ; Annuler laisse l’espace de travail inchangé, tandis que OK réutilise un aperçu courant terminé pour une source unique et exécute sinon le traitement normal sur la sélection initiale.

  • Les aperçus terminés conservent leur processus dédié prêt pour les boîtes de dialogue suivantes, ce qui évite des démarrages de processus répétés. L’annulation d’un aperçu encore en cours arrête son processus afin qu’aucun calcul spéculatif ne se poursuive en arrière-plan.

  • Les paramètres numériques bornés proposent désormais des curseurs en complément d’une saisie textuelle précise. L’onglet Traitement conserve Appliquer et le retraitement automatique, avec des mises à jour différées jusqu’au relâchement du curseur et à une saisie valide.

Statut des plugins :

  • Cliquez sur le libellé Plugins : de la barre de statut pour ouvrir Configurer les plugins…, comme avec les libellés de statut de l’API Web et de la console interne. Le raccourci est disponible lorsque les plugins sont globalement activés, y compris lorsqu’aucun plugin n’est chargé ou qu’un plugin n’a pas pu être chargé.

Plugins d’application :

  • Ajout d’une entrée de premier niveau Applications qui présente les plugins d’application scientifique actifs dans un nouveau panneau Applications

  • Chaque application affiche sa description, sa version, ses méthodes, ses outils et ses exemples ; les plugins de traitement seul restent en dehors de cette vue ciblée

  • Chaque méthode présente les entrées qu’elle attend (type et nombre d’objets, métadonnées requises) et un statut mis à jour indiquant si la sélection courante peut être analysée, et sinon pourquoi

  • Lorsque des métadonnées requises manquent, le statut renvoie vers Édition > Métadonnées > Ajouter des métadonnées…, dont la liste Clés connues propose aussi les clés attendues par les méthodes des applications ; le statut est mis à jour dès que des objets sont modifiés

  • Exécuter… lance directement une méthode sur la sélection courante lorsque celle-ci convient, et ne demande l’affectation des entrées que si elle est ambiguë ou invalide ; la boîte de dialogue d’affectation vérifie les objets choisis avant de permettre l’exécution

  • Les exemples sont listés sous les méthodes pour lesquelles ils sont conçus : Essayer avec cet exemple ouvre l’exemple, préremplit les paramètres de la méthode et exécute celle-ci une fois qu’ils sont acceptés. Un exemple peut servir plusieurs méthodes, et les exemples conçus pour aucune méthode sont listés comme jeux de données

  • Les plugins d’application peuvent aussi lister des outils, comme des assistants ou des éditeurs, dans le panneau Applications

  • Les outils de plugin apparaissent aussi dans le sous-menu du plugin du menu Plugins, dans le panneau Signal ou Image sur lequel ils travaillent. Un outil qui a besoin d’une sélection est désactivé jusqu’à ce que les bons objets soient sélectionnés, et son bouton dans le panneau Applications indique quoi sélectionner

  • Les plugins d’application peuvent fournir des instruments, comme des caméras ou des oscilloscopes simulés, sans écrire d’interface utilisateur : DataLab affiche une fenêtre avec une vue en direct et les réglages de l’instrument, rafraîchie à chaque modification des réglages ou en continu en mode En direct, et Acquérir ajoute les objets acquis dans un nouveau groupe, prêts pour les méthodes de l’application

  • L’option Nouveau groupe de la fenêtre d’instrument peut être désactivée pour ajouter les acquisitions suivantes au groupe courant du panneau, au lieu de créer un groupe pour chacune d’elles. L’option et le groupe courant sont pris en compte au clic sur Acquérir, de sorte que sélectionner un autre groupe pendant une acquisition ne change pas sa destination. Chaque instrument définit l’état par défaut de l’option, et le choix de l’utilisateur est mémorisé pour chaque instrument

  • Les instruments sont appelés en dehors du fil d’exécution de l’interface utilisateur, un appel à la fois : un instrument lent, comme un appareil réel attendant ses données, ne fige plus DataLab, et les demandes de rafraîchissement répétées entre-temps sont regroupées. Les instruments peuvent aussi déclarer des méthodes open et close, appelées à l’ouverture et à la fermeture de leur fenêtre (y compris lors du rechargement des plugins ou de la fermeture de DataLab), par exemple pour se connecter à un appareil puis le libérer. Les appels restent successifs lorsqu’une fenêtre est fermée puis rouverte pendant un appel. Lorsque open échoue, son message reste affiché dans la fenêtre et l’instrument est ouvert à nouveau avant le rafraîchissement ou l’acquisition suivant, par exemple après une modification des réglages

  • Les développeurs de plugins décrivent les entrées des recettes de manière déclarative (titres, effectifs minimaux, métadonnées requises) et peuvent ajouter des suggestions d’affectation et des vérifications rapides des entrées ; chaque recette s’exécute alors via le lanceur générique de DataLab, sans boîte de dialogue d’entrées propre au plugin

  • Le panneau Applications est un panneau comme les autres, qui ne masque pas l’espace de travail de DataLab : la première fois, il s’affiche en fenêtre flottante à côté de la fenêtre principale, sur toute la hauteur de celle-ci, afin que les données et leurs vues restent visibles pendant son utilisation. Il peut ensuite être ancré (par exemple à côté de la liste des signaux ou des images dont il analyse la sélection), regroupé en onglets avec un autre panneau ou laissé flottant, et DataLab l’affiche à nouveau là où l’utilisateur l’a laissé, avec la même taille ; lorsqu’il est demandé alors qu’il est déjà affiché, sans changer d’application, il clignote brièvement pour indiquer où il se trouve. Il reste ouvert après le lancement d’une méthode ou l’ouverture d’un exemple

  • Le panneau reste compact et lisible lorsqu’il est ancré : chaque méthode occupe une ligne, avec une pastille de couleur et un court texte indiquant si la sélection courante peut être analysée, et un bouton Exécuter… ; sous la liste, une zone Détails donne tous les détails de la méthode sélectionnée (description, raisons de son statut, entrées attendues avec la description et la clé de leurs métadonnées, exemples). Le résultat de la dernière exécution d’une méthode s’affiche sous sa ligne. Les sections de la liste peuvent être repliées, et la hauteur des détails réglée à l’aide d’un séparateur : DataLab mémorise ces choix

  • Lorsque plusieurs plugins d’application sont installés, leur nombre est indiqué en haut du panneau, au-dessus de la liste permettant de choisir l’application ; la documentation et les options de page d’accueil de l’application se trouvent dans le menu situé à côté

  • Les méthodes d’application terminées sélectionnent le dernier objet qu’elles ont généré, de manière cohérente avec les traitements standard de DataLab

  • Les plugins d’application ajoutent des tuiles à une nouvelle section Applications de la page d’accueil : par défaut, une tuile par plugin affiche sa page dans le panneau Applications, et les plugins peuvent déclarer des tuiles supplémentaires, par exemple pour ouvrir directement un exemple. Les tuiles supplémentaires sont affichées lorsqu’il y a la place nécessaire, et passent sinon dans le menu de la tuile principale

  • La page d’accueil reste lisible lorsque de nombreuses applications sont installées : les tuiles sont limitées à un nombre de lignes configurable (deux par défaut), une dernière tuile affichant le panneau Applications pour les autres. Les applications peuvent être épinglées en tête ou masquées, et celles utilisées récemment viennent en premier ; le panneau Applications propose les mêmes options de page d’accueil

  • Les plugins peuvent déclarer une icône, affichée dans le panneau Applications, sur leur tuile de la page d’accueil et dans la boîte de dialogue Configurer les plugins…

  • DataLab vérifie les déclarations des plugins d’application (méthodes, exemples, outils, tuiles de la page d’accueil) lors de leur chargement : un plugin dont une déclaration est invalide, par exemple une méthode dont la version du plugin n’a pas été mise à jour avec celui-ci, ou un exemple faisant référence à une méthode renommée, n’est pas chargé et est listé avec son erreur dans Configurer les plugins…, tandis que DataLab et les autres plugins démarrent normalement (corrige l’issue #484)

Installation de plugins :

  • Les catalogues Desktop en ligne et hors ligne acceptent désormais les plugins en fichier unique datalab_*.py à côté des wheels. Les fichiers historiques n’ont besoin ni de projet de packaging ni de modification du code source pour être référencés ; l’inspection du catalogue ne les importe ni ne les exécute jamais (implémente l’issue #419)

  • Les versions connues des scripts peuvent être mises à jour ; les fichiers sans version sont identifiés par SHA-256 et proposent un remplacement explicite lorsque leur contenu change. Les scripts précédemment installés depuis un fichier sont reconnus et les copies de développement existantes ne sont pas écrasées

  • Les commandes de catalogue local gèrent les dossiers mêlant scripts et wheels. Les plugins en fichier unique utilisent les bibliothèques déjà disponibles dans DataLab et ne déclenchent pas de téléchargement de dépendances. La documentation distingue désormais explicitement l’organisation du code source, les formats de distribution et les capacités fonctionnelles, y compris dans le guide hors ligne français

  • Les plugins peuvent désormais être installés depuis un fichier, sans aucun outil Python, y compris dans la version autonome de DataLab : le nouvel onglet Depuis un fichier de Plugins > Configurer les plugins… accepte un wheel en Python pur (.whl) ou un module unique datalab_<nom>.py

  • Avant l’installation, DataLab vérifie le fichier sans l’exécuter et affiche son nom, sa version, ses classes de plugins, ses dépendances et son empreinte SHA-256

  • Les plugins peuvent désormais fournir des dépendances supplémentaires sous forme de paquets wheel séparés, y compris des bibliothèques natives compatibles, sans modifier les paquets déjà fournis par DataLab. Un catalogue local complet peut être installé sans accès à Internet ; les fichiers manquants et les conflits de versions sont signalés avant toute activation d’une installation partielle

  • La boîte de dialogue de confirmation liste les paquets supplémentaires et leurs empreintes. Ils sont partagés entre les plugins d’un même environnement d’exécution Python, activés après redémarrage de DataLab et conservés lorsqu’un plugin est désinstallé

  • Les plugins installés sont listés dans le même onglet, où ils peuvent être désinstallés ; un plugin nouvellement installé est activé après rechargement si aucun paquet supplémentaire n’est nécessaire, ou après redémarrage si des dépendances ont été ajoutées. Une nouvelle version d’un plugin déjà chargé est utilisée au prochain démarrage

  • Le nouvel onglet Catalogue liste les plugins du catalogue de plugins DataLab, officiels ou issus de la communauté, avec un champ de recherche : Installer et Mettre à jour téléchargent le wheel, le vérifient par rapport au catalogue et l’installent après confirmation. L’adresse du catalogue peut être modifiée pour utiliser une copie privée

  • Les organisations peuvent diffuser leurs propres plugins, ou les versions de plugins publics qu’elles ont validées, depuis des catalogues locaux de plugins : des dossiers, généralement partagés sur le réseau, déclarés dans l’onglet Avancé ou par la variable d’environnement DATALAB_PLUGINS_CATALOG. Leurs plugins sont listés dans l’onglet Catalogue avant ceux du catalogue de plugins DataLab, et les masquent lorsque les deux proposent le même plugin

  • Un dossier de catalogue local peut contenir des wheels et des modules en fichier unique, listés à mesure qu’ils y sont copiés, ou un index catalog.json indiquant les noms d’affichage, les dépréciations et les versions retirées ; datalab-plugin catalog build écrit cet index en conservant les métadonnées administrées, et datalab-plugin catalog check signale les fichiers manquants, modifiés, refusés ou non listés

  • Les auteurs peuvent préparer un catalogue hors ligne avec datalab-plugin catalog prepare : la commande télécharge les paquets de dépendances supplémentaires nécessaires à l’environnement hôte de référence sans les installer, puis écrit le catalogue. Le dossier complet peut être distribué sur un partage réseau ou copié sur des ordinateurs sans accès à Internet

  • Un catalogue illisible, comme un partage réseau non connecté ou le catalogue en ligne sur un ordinateur sans accès à Internet, est signalé dans l’onglet Catalogue sans masquer les plugins des autres catalogues

  • La boîte de dialogue Configurer les plugins… s’ouvre plus grande et conserve la taille qu’elle avait à sa dernière fermeture. Ses onglets suivent l’ordre d’utilisation et ont des titres explicites, décrits par leurs info-bulles : Installés, Catalogue, Depuis un fichier et Avancé

Générateur de projets de plugins :

  • datalab-plugin create crée désormais par défaut un plugin en fichier unique, la façon la plus simple d’étendre DataLab : la commande demande seulement le nom du plugin et sa description, puis écrit un fichier datalab_<nom>.py dans le répertoire de plugins de l’utilisateur. Une fois les plugins rechargés, le plugin ajoute son sous-menu au menu Plugins, avec un traitement d’exemple des signaux sélectionnés (ou des images, avec --object-kind image), dont la courte fonction NumPy est la seule partie à modifier. Le fichier n’écrase jamais un fichier existant, et peut être partagé et installé avec Plugins > Configurer les plugins… > Depuis un fichier. Le projet installable structuré en couches, décrit ci-dessous, est créé avec --project (implémente l’issue #413)

  • Durcissement de datalab-plugin create à partir du retour du pilote Camera : les projets générés séparent désormais dès le premier commit le code core indépendant de l’hôte, l’orchestration workflow sans interface et les adapters Desktop/Web

  • La racine des packages générés expose une identité stable sans importer Qt ; le point d’entrée installé cible l’adaptateur Desktop, tandis que la prise en charge Web est explicitement marquée comme non prise en charge

  • Chaque projet généré comprend un test de non-régression exécutable de l’architecture, une documentation de contribution et d’architecture, ainsi qu’un changelog

  • Les noms et descriptions de plugins longs sont désormais mis en forme afin que les projets nouvellement générés réussissent leurs contrôles Ruff intégrés sans modification manuelle du code source

  • Les projets générés sont prêts à publier : un workflow de release joint le wheel à une release GitHub lorsqu’une étiquette de version est poussée et affiche la fiche à soumettre au catalogue de plugins DataLab ; pyproject.toml exige la version majeure courante de DataLab et déclare les URL du projet

  • datalab-plugin create --project demande le compte GitHub qui héberge le projet et en déduit l’ID de plugin par défaut (io.github.<compte>.<nom>), les ID org.datalab. étant réservés aux plugins de DataLab-Platform

Ajout de métadonnées :

  • Édition > Métadonnées > Ajouter une métadonnée… peut désormais extraire la valeur du texte formaté avec une expression régulière, par exemple un temps d’exposition ou un numéro de tir lu dans les titres des objets. Les objets sans correspondance restent inchangés, sauf si vous demandez une erreur, et un facteur d’échelle convertit les valeurs numériques (par exemple des millisecondes en secondes)

  • Les clés de métadonnées peuvent désormais contenir des points et des tirets, comme les clés des plugins, et une liste Clés connues copie une clé déjà présente sur les objets sélectionnés

Provenance de l’espace de travail :

  • DataLab enregistre désormais la manière dont chaque résultat a été obtenu : le traitement appliqué, ses paramètres, les objets utilisés et leur contenu exact, ainsi que les versions des logiciels. Cet enregistrement est sauvegardé avec l’espace de travail HDF5 et relu à sa réouverture, par DataLab ou par DataLab-Web : l’historique d’un résultat survit ainsi à l’enregistrement, à la fermeture et au partage

  • Les traitements de signaux et d’images, les opérations combinant plusieurs objets et les analyses (résultats géométriques et tableaux) sont enregistrés, chacun avec l’identité de son opération Sigima ; les régions d’intérêt, les incertitudes, l’alignement en X appliqué aux signaux sur des grilles différentes et les options globales lues par le calcul (comme la normalisation des noyaux) font partie de l’enregistrement, et les signaux et images de tous les types numériques (float32, complexes…) sont couverts. Une analyse qui ne trouve rien est enregistrée comme telle. Un résultat dont les données, l’étalonnage ou les régions d’intérêt ont été modifiés après son calcul est signalé comme altéré plutôt que considéré comme fiable

  • Tout traitement ou toute analyse enregistrés d’une opération Sigima qualifiée (toutes sauf le spectre de phase) peuvent être recalculés et chaque résultat comparé au résultat stocké : exactement, ou dans la tolérance déclarée pour l’opération lorsque les bibliothèques numériques diffèrent (exact, dans la tolérance, différent, ou non vérifié avec la raison). Le recalcul est disponible depuis l’onglet Provenance du panneau des propriétés (Vérifier le calcul) et depuis les scripts ; il ne modifie jamais l’espace de travail. Lorsque seules les régions d’intérêt d’une entrée ont changé depuis le calcul (par exemple des régions créées sur l’image analysée par une détection), il est effectué sur une copie portant les régions d’intérêt enregistrées, si bien qu’une telle analyse reste vérifiable

  • L’onglet Historique du panneau des propriétés est renommé Provenance (pour éviter toute confusion avec le panneau Historique) et affiche désormais la provenance de l’objet sélectionné : l’exécution enregistrée qui a produit son contenu actuel, ses paramètres et ses entrées, et, étape par étape, la manière dont chaque entrée a elle-même été produite, telle qu’elle était à ce moment-là (par exemple le sigma réellement utilisé, même si l’entrée a été filtrée à nouveau depuis), avec le logiciel qui l’a enregistrée (DataLab Desktop ou DataLab Web). Chaque étape est une fiche avec ses paramètres, ses entrées et ses résultats, et des liens placés à côté de ce sur quoi ils agissent : afficher l’étape enregistrée d’une entrée, Aller à l’objet, Vérifier cette étape, Action de l’historique et détails. Contrôler les données compare l’objet, ses entrées directes et les étapes antérieures affichées à leurs états enregistrés sans calculer ; les entrées supprimées sont signalées immédiatement, les entrées modifiées ou indisponibles après contrôle. Aller à l’action de l’historique d’une étape laisse l’onglet Provenance ouvert

  • L’onglet Traitement restaure l’appel enregistré du résultat sélectionné, y compris pour les opérations combinant plusieurs objets (différence de deux signaux, moyenne de plusieurs images…) : chaque entrée est conservée dans l’ordre avec son rôle, les paramètres peuvent être modifiés, et les traitements sans paramètres proposent un bouton Réappliquer. Lorsque le traitement ne peut pas être appliqué à nouveau (par exemple si une entrée a été supprimée), l’onglet en indique la raison. Cela fonctionne aussi pour les espaces de travail rouverts depuis un fichier, enregistrés par DataLab ou par DataLab-Web

  • Les actions de l’historique sont liées à la provenance de leur dernière exécution réussie : Afficher la provenance de l’exécution dans le panneau Historique l’affiche, et la provenance d’un résultat mène à l’action de l’historique qui l’a produit, analyses comprises. En mode d’édition du panneau Historique, modifier l’un des résultats d’une commande en produisant plusieurs ne change que ses paramètres dans l’action

  • Lorsqu’un fichier d’espace de travail contenant une provenance est ajouté à l’espace de travail actuel (sans le vider), DataLab indique désormais, avant toute modification, que sa provenance antérieure ne sera pas importée : dans la question proposant de vider l’espace de travail (les fichiers sont choisis d’abord), ou dans un avertissement unique lorsque cette question n’est pas posée. Les objets ajoutés n’héritent jamais de la provenance d’un autre objet (ils ne sont ni affichés ni utilisés comme entrée d’origine d’une étape enregistrée, y compris lors de sa vérification), et leurs traitements ultérieurs sont enregistrés

  • DataLab Desktop et DataLab-Web enregistrent les mêmes traitements de manière identique et rejouent les résultats l’un de l’autre

  • Avant d’interpoler des signaux dont les grilles en X diffèrent, DataLab demande toujours confirmation ; l’alignement appliqué est celui qu’il a toujours appliqué, désormais nommé et enregistré afin qu’un recalcul l’applique à l’identique. Lorsque plusieurs paires sont sélectionnées pour une opération sur deux signaux, chacune aligne désormais l’opérande sur la grille de son propre signal source

  • Les espaces de travail enregistrés par des versions antérieures conservent leur historique de traitement tel qu’il a été stocké : DataLab montre ce qui est connu et ce qui manque, n’invente rien, et ne recalcule jamais ces entrées

  • Un espace de travail dont l’enregistrement de provenance est endommagé est refusé avec un message explicite, et l’espace de travail actuel reste inchangé

  • Les espaces de travail peuvent être échangés sous forme de capsules (un espace de travail et une description de sa provenance) depuis Fichier > Capsule d’espace de travail…, la même boîte de dialogue que dans DataLab-Web, afin qu’une autre personne puisse les vérifier et les rejouer avec l’une ou l’autre édition :

    • Exporter l’espace de travail, avec un nom, une description, des pièces jointes légères (protocole, notes, petits tableaux) et, pour un espace de travail ouvert depuis une capsule (y compris après l’avoir enregistré puis rouvert), la capsule dont il est une révision ; l’espace de travail peut aussi être référencé par son adresse de publication au lieu d’être inclus

    • Inspecter une capsule sans l’ouvrir : ses activités, ses pièces jointes (enregistrées seulement à la demande, jamais ouvertes), son intégrité (espace de travail et états enregistrés vérifiés, rien n’est recalculé) et les rapports de vérification et revues fournis avec elle, chacun vérifié par rapport à la capsule ; en rédiger une revue, ou Ouvrir comme espace de travail (action enregistrée dans le panneau Historique)

    • Rejeu local recalcule une activité enregistrée de l’espace de travail ouvert et la compare à son résultat enregistré, sans modifier l’espace de travail ; le rapport de vérification peut être enregistré pour être partagé avec la capsule

    • Révisions énumère les capsules exportées, inspectées ou récupérées sur cet ordinateur et compare deux d’entre elles (changements scientifiques, de présentation, de stockage, d’environnement et de pièces jointes)

    • Registre se connecte à un registre de capsules facultatif pour publier des capsules (jamais leurs espaces de travail) et des revues, lister les révisions publiées et les récupérer, tout ce qui est renvoyé étant vérifié

    • Les scripts et les macros peuvent aussi exporter et ouvrir des capsules (export_capsule et open_capsule du proxy), et la ligne de commande workspace-capsule de DataLab-Capsule permet toujours de les valider, de les comparer et de les vérifier

    • Une capsule, ou l’espace de travail qu’elle référence, qui dépasse la limite de taille est refusée avant d’être lue, et DataLab n’écrit jamais une capsule qu’il refuserait d’ouvrir, ni la capsule ou son espace de travail référencé l’un sur l’autre ou sur une pièce jointe ; les limites et les coûts mesurés sont indiqués dans la page Capsules d’espace de travail

    • La version autonome (installeur) embarque ce dont les capsules ont besoin (schémas et contexte RO-Crate de DataLab-Capsule)

Références aux objets dans les titres :

DataLab utilise désormais des références aux objets stables, fondées sur les UUID, dans les arborescences d’objets, les titres de résultats, les légendes des graphiques et les espaces de travail HDF5 (implémente Issue #367 et Issue #149).

  • Les signaux, images et groupes des arborescences affichent désormais leur titre courant suivi de leur propre référence stable #UUID8 (#gUUID8 pour les groupes), à la place des anciens identifiants s001, i001 et gs001

  • Les références aux sources intégrées dans les titres de résultats ne changent plus lorsque des objets sont réordonnés, supprimés ou renumérotés, et restent cliquables pour sélectionner l’objet source

  • Le nouveau paramètre Références dans les titres de résultats permet d’afficher ces références soit sous forme d’UUID à 8 caractères (par défaut), soit avec les titres actuels des sources, qui suivent les renommages ultérieurs et sont résolus sur l’ensemble des chaînes de traitement (par exemple derivative(derivative(Mon signal)))

  • Lorsqu’un objet source est supprimé, sa référence est affichée sous la forme de son UUID à 8 caractères au lieu de devenir un espace réservé anonyme

  • Les titres des espaces de travail enregistrés par les versions précédentes conservent leurs anciennes références de type s001 sous forme de texte simple

Listes de signaux et d’images :

Les signaux, images et groupes peuvent désormais être supprimés directement depuis les listes, comme dans DataLab-Web (implémente l’issue #449).

  • Un bouton de suppression apparaît à droite du signal, de l’image ou du groupe survolé : il devient rouge lorsque le curseur de la souris le survole, et son info-bulle indique ce qu’il supprime

  • Un clic sur ce bouton supprime l’élément, ou toute la sélection lorsque l’élément en fait partie, après confirmation. Supprimer un élément non sélectionné laisse inchangés la sélection courante et les objets affichés

  • Comme avec l’action Supprimer, la suppression est enregistrée dans le panneau Historique

  • Le bouton peut être masqué avec le nouveau paramètre Afficher un bouton de suppression au survol des éléments des listes (Visualisation > Commun)

Formules des modèles d’ajustement :

  • Les fenêtres d’ajustement interactif affichent désormais la formule du modèle ajusté sous les paramètres d’ajustement, et le libellé de chaque paramètre indique son symbole dans la formule (par exemple « Facteur d’échelle (x₀) ») : les paramètres enregistrés dans les métadonnées du signal ajusté peuvent ainsi être reliés au modèle sans lire le code source. La documentation Ajustement indique également, pour chaque modèle, le nom sous lequel chaque paramètre est enregistré (corrige l’issue #400)

  • Les coefficients des ajustements polynomial et linéaire sont nommés a, b, c… comme dans la formule et dans les métadonnées, au lieu de c2, c1, c0

  • La documentation Ajustement explique comment déduire la longueur d’onde du pic, la température et l’émissivité des paramètres d’un ajustement planckien

Contrôle à distance et plugins :

  • Le plugin Tracé de contours d’isoniveau (org.datalab.isolevel-map, version 1.1.0), auparavant fourni comme exemple de plugin, est désormais un plugin intégré disponible directement depuis Plugins > Tracé de contours d’isoniveau > Afficher le tracé de contours…

  • add_group renvoie désormais l’UUID du groupe créé, de sorte qu’un client distant, une macro ou un plugin peut y ajouter des objets avec add_object(obj, group_id=...) (ou add_signal/add_image) au lieu de rechercher le groupe par son titre

  • load_from_files et load_from_directory acceptent désormais un argument optionnel param contenant les paramètres d’import propres au format (par exemple RawImageImportParam pour les images RAW), appliqués sans afficher de boîte de dialogue

Fichiers NeXus :

  • Les groupes NeXus NXdata sont présentés comme des éléments uniques dans l’explorateur HDF5 et importés comme signaux ou images avec leurs axes, unités, libellés et, pour les signaux, incertitudes. Les bords de classes sont convertis en centres de classes, les axes d’image non uniformes sont conservés, et les axes d’image décroissants sont inversés avec l’image. Les axes invalides sont signalés dans l’explorateur au lieu d’être devinés

  • Les fichiers écrits selon les conventions NeXus anciennes, comme les scans du synchrotron SOLEIL, sont importés avec leurs axes (attributs axis et primary des jeux de données d’axe), et chaque compteur et détecteur d’un scan apparaît comme un élément à part entière : les compteurs comme des signaux en fonction du moteur scanné, les détecteurs comme des images (un spectre par point) ou des piles d’images (une image par point) avec le moteur selon leur premier axe

  • Le navigateur HDF5 sélectionne et affiche la mesure par défaut d’un fichier NeXus (attributs default) à son ouverture

  • Les données de détecteur compressées, comme les données bitshuffle/LZ4 des détecteurs Eiger, sont désormais lues (avec hdf5plugin, y compris dans l’application autonome) ; un jeu de données compressé avec un filtre indisponible est signalé dans le navigateur au lieu de provoquer une erreur

  • Les signaux et images importés enregistrent leur origine (fichier, groupe, signal et axes, conversions appliquées, titre et dates de l’entrée NeXus) dans leurs métadonnées experimental_source, enregistrées avec l’espace de travail : un espace de travail enregistré se rouvre sans le fichier NeXus

  • Les fichiers .nxs et .nx5 sont proposés à l’ouverture de fichiers HDF5

  • Les plugins peuvent décrire les signaux et images des fichiers dont les groupes NeXus NXdata sont incomplets (pas d’axes, plusieurs compteurs…) avec des profils de correspondance déclaratifs (JSON) enregistrés par sigimax.h5.mapping.register_mapping : le navigateur HDF5 affiche alors chaque objet décrit comme un élément supplémentaire, importé avec ses axes, libellés et unités ; les axes d’un objet décrit peuvent ne décrire que ses premières dimensions, de sorte qu’un même profil s’applique aux compteurs et aux détecteurs d’un scan

Vérification de l’installation :

  • La nouvelle option de ligne de commande --smoke-test vérifie que DataLab est correctement installé sans ouvrir sa fenêtre principale, par exemple DataLab.exe --smoke-test report.json pour la version autonome ou datalab --smoke-test report.json : les packages dont il dépend, les ressources fournies avec lui (modèles de macros, documentation PDF, traductions françaises et icônes) et le traitement dans un processus séparé. Les résultats sont écrits dans un rapport JSON, et le code de sortie est non nul lorsqu’une vérification a échoué (voir Fonctionnalités de la ligne de commande)

  • Avant sa publication, chaque installeur Windows est désormais installé sur un ordinateur de test, où l’application installée est démarrée puis vérifiée de cette façon (implémente l’issue #366)

🔄 Changements#

Lisibilité des courbes :

  • Les courbes des signaux sont plus lisibles, en particulier lorsque de nombreuses courbes sont affichées (corrige l’issue #453) :

    • Les couleurs des courbes ressortent désormais sur fond clair comme sur fond sombre : plusieurs couleurs de l’ancienne palette (orange, rose, vert-jaune, cyan) étaient pâles sur fond blanc, et les courbes grises se confondaient avec la grille

    • Au-delà des 10 premières courbes, les courbes sont désormais tracées uniquement en tirets : les traits mixtes (tiret-point et tiret-point-point), qui ne traçaient que la moitié de la courbe, ne sont plus utilisés

    • La grille des graphiques utilise désormais des traits pleins discrets au lieu de pointillés gris, qui se confondaient avec les courbes en tirets ; elle suit également les changements de thème de couleurs

  • Les couleurs et les styles de trait des courbes dépendent désormais de la position des courbes parmi celles affichées dans le graphique, dans l’ordre des signaux du panneau : la première courbe affichée est toujours tracée avec la première couleur. L’ouverture de l’éditeur de ROI, de Voir dans une nouvelle fenêtre ou d’autres boîtes de dialogue ne décale plus les styles des courbes suivantes, ce qui pouvait faire apparaître des pointillés avec seulement quelques courbes affichées

  • Les styles de courbes automatiques ne sont plus enregistrés dans les espaces de travail : seuls une couleur ou un style de trait choisis par l’utilisateur sont enregistrés et toujours conservés, quelle que soit leur valeur. À l’ouverture des espaces de travail et des fichiers d’historique enregistrés avec DataLab 1.3 ou une version antérieure, qui enregistraient le style automatique de chaque courbe, ces styles sont supprimés afin que les courbes soient affichées avec les nouveaux styles automatiques ; un style choisi avec ces versions est également supprimé lorsqu’il est identique à l’un de leurs styles automatiques. Les métadonnées importées depuis un fichier sont appliquées telles quelles

  • Affichage > Réinitialiser les styles de courbes rend désormais aux signaux sélectionnés des styles de courbes automatiques, en supprimant les couleurs et les styles de trait choisis pour eux

  • Sur les écrans haute résolution (par exemple avec une mise à l’échelle de l’affichage de 150 %), les courbes d’épaisseur 1 sont désormais tracées avec une largeur d’un pixel de l’écran, ce qui rend leur tracé beaucoup plus rapide : les signaux bruités étaient tracés jusqu’à plusieurs centaines de fois plus lentement qu’à 100 % (nécessite PlotPy ≥ 2.12.0)

Images synthétiques en coordonnées physiques :

  • Les images gaussienne 2D, rampe 2D, réseau sinusoïdal, anneaux, mire de Siemens et sinus cardinal 2D étaient calculées sur le domaine [xmin, xmax] × [ymin, ymax] de leurs paramètres de création, mais étaient affichées en coordonnées pixel : leurs centres, largeurs et fréquences spatiales ne correspondaient pas aux axes (un réseau sinusoïdal de fréquence 0,1 sur [0, 100] présentait 10 périodes le long d’un axe gradué de 0 à 1023). Ces images sont désormais affichées sur leur domaine. La nouvelle option Coordonnées physiques de leurs paramètres de création rétablit les coordonnées pixel lorsqu’elle est désactivée (corrige l’issue #400)

  • Les images créées avec des versions antérieures conservent leurs coordonnées pixel lorsque leurs paramètres de création sont modifiés ou recalculés

Visite guidée :

  • La visite guidée ne démarre plus automatiquement au premier lancement : elle est désormais proposée depuis la page d’accueil, et reste disponible depuis le menu ?

Réactivité avec les grandes campagnes :

  • L’ouverture, la sélection et l’affichage de grandes campagnes générées ne répètent plus un rafraîchissement complet de l’espace de travail et des graphiques pour chaque objet

  • Les espaces de travail HDF5 natifs et les résultats de méthodes multi-objets se chargent désormais par lots, ce qui rend les grandes collections de signaux et d’images disponibles nettement plus vite tout en préservant chaque objet sélectionné et visible

Réactivité de l’affichage des images :

  • Le déplacement ou le redimensionnement de régions d’intérêt, d’annotations et de marqueurs sur les images est désormais beaucoup plus fluide, car l’image n’est plus recalculée à chaque mouvement de la souris : avec une image de 2048 × 2048 pixels, chaque mouvement de la souris prend environ 5 ms au lieu de 13 ms (13 ms au lieu de 33 ms avec une mise à l’échelle de l’affichage de 200 %). Le déplacement et le zoom des images sans pixels masqués sont également jusqu’à 25 % plus rapides (nécessite PlotPy ≥ 2.12.1)

Icônes nettes avec la mise à l’échelle de l’affichage :

  • Les icônes des graphiques et des éditeurs fournies par PlotPy et guidata (barres d’outils des graphiques, panneau de contraste, coupes, liste des éléments, éditeur de tableaux, …) sont désormais des images SVG : elles restent nettes avec une mise à l’échelle de l’affichage de 125 %, 150 % ou 200 %, au lieu d’apparaître floues (nécessite PlotPy ≥ 2.12.1, corrige l’issue #470)

  • L’action Traitement > Redimensionner des images affichait l’icône de redimensionnement des colonnes des éditeurs de guidata au lieu de sa propre icône : les icônes de DataLab ont désormais priorité sur les icônes de guidata et de PlotPy portant le même nom (nécessite guidata ≥ 3.17.1, corrige l’issue #472)

  • Les icônes des plugins (PluginInfo.icon, outils et tuiles de la page d’accueil) peuvent également désigner une icône enregistrée par un module, par exemple "datalab:delete.svg", en plus des ressources package:path et des noms de fichiers d’icônes de DataLab

Annotations de tracé portables :

  • Les annotations de tracé sont désormais stockées dans un format indépendant du moteur de rendu, partagé avec DataLab-Web, de sorte que les annotations dans les espaces de travail et les fichiers .dlabann ne sont plus liées à PlotPy

  • Les annotations PlotPy existantes restent lisibles et ne sont converties qu’après qu’une modification d’annotation a été acceptée ; ouvrir simplement un espace de travail ou annuler l’éditeur laisse ses données inchangées

  • Les identifiants d’annotation, l’état de verrouillage, les métadonnées personnalisées et les données d’extension sont conservés lors des modifications, tandis que les charges utiles tierces inconnues sont conservées sans modification

  • Les rectangles et segments tracés sur les signaux sont désormais les mêmes formes avec étiquette que sur les images ; contrairement aux images, les segments tracés sur les signaux n’affichent pas leur longueur et leur angle, qui mélangeraient les unités de X et de Y

Régions d’intérêt :

  • Une région d’intérêt rectangulaire sélectionne désormais les pixels dont le centre est situé dans le rectangle, bornes comprises, comme les ROI circulaires et polygonales et comme l’affichage : ses bornes étaient arrondies au pixel le plus proche, ce qui pouvait décaler la sélection jusqu’à un demi-pixel. Un rectangle dont les bornes sont situées exactement sur des centres de pixels inclut désormais les pixels des deux bornes, soit une ligne et une colonne de plus qu’auparavant. Cela s’applique aux traitements et analyses dans les ROI, à l’extraction de ROI et à la zone de fond de la soustraction d’offset

  • Les régions d’intérêt circulaires et polygonales sélectionnent elles aussi désormais les pixels dont le centre est situé dans leur forme, bord compris : les sommets des polygones étaient arrondis au pixel le plus proche, de sorte que les pixels sélectionnés pouvaient différer du polygone tracé sur l’image, et les cercles étaient tracés en unités de pixels sur les images à coordonnées non uniformes

  • Une ROI rectangulaire définie en indices de pixels couvre désormais ses pixels jusqu’à leurs bords extérieurs, de sorte qu’elle conserve les mêmes pixels lorsqu’elle est convertie en coordonnées physiques et inversement

  • Les cellules des grilles de ROI (ROI > Créer une grille de ROI…) sont désormais formées de pixels entiers, de sorte que des cellules adjacentes n’ont jamais de pixel en commun et qu’une grille pleine couvre chaque pixel exactement une fois, quelle que soit la taille de l’image ; sur les images à coordonnées non uniformes, la grille couvre désormais toute l’image, dont les dernières lignes et colonnes étaient omises

  • Les régions d’intérêt enregistrées avec des versions antérieures ne sont pas converties : elles sélectionnent les pixels selon ces règles lorsqu’elles sont réutilisées, de sorte que les traitements et analyses dans ces régions peuvent donner des résultats légèrement différents lorsqu’ils sont recalculés

Profils d’image en coordonnées physiques :

  • Les profils rectilignes, de segment, moyens et radiaux (Analyse > Profils d’intensité) sont désormais définis dans les coordonnées physiques de l’image, comme les régions d’intérêt et les résultats d’analyse, au lieu d’indices de pixels : les paramètres des profils indiquent des coordonnées dans les unités des axes de l’image, et l’axe X des signaux obtenus contient des coordonnées ou des distances physiques avec l’unité correspondante. Sur les images sans calibration (origine 0, taille de pixel 1), les résultats sont inchangés

  • Le profil radial est désormais circulaire sur les images à pixels rectangulaires ou à coordonnées non uniformes, et son centre est correct sur les images calibrées, où le centre de l’image était mal placé

  • Les profils de segment et radiaux sont refusés sur les images dont les unités X et Y diffèrent, les distances n’étant alors pas définies ; les coordonnées hors de l’image sont refusées au lieu d’être ramenées silencieusement au bord. Les lignes et segments tracés au-delà de l’image dans la boîte de dialogue de profil sont ramenés à ses pixels extrêmes

  • Les scripts, macros et plugins doivent utiliser les nouveaux noms de paramètres (y/x pour les profils rectilignes, x1, y1, x2, y2 pour les profils de segment et moyens, xc/yc pour les profils radiaux) et des coordonnées physiques. Les calculs de profils enregistrés dans la provenance d’espaces de travail sauvegardés avec des versions antérieures sont signalés comme non vérifiables, au lieu d’être rejoués avec une signification différente

Explorateur HDF5 :

  • Parcourir un fichier HDF5 ne lit plus ses jeux de données en entier : ils sont listés et décrits à partir de leur forme et de leur type de données, et les aperçus de valeurs ne lisent que leurs premiers éléments. Les gros fichiers s’ouvrent plus vite et utilisent moins de mémoire ; les données sont lues lorsqu’un signal ou une image est prévisualisé ou importé

  • L’explorateur HDF5 reste réactif pendant la lecture d’un aperçu, et les éléments sélectionnés entre-temps ne sont pas lus ; la sélection d’un élément qui ne peut pas être prévisualisé (un groupe, par exemple) efface l’aperçu. Les tableaux 1D ordinaires et les images 2D, les objets NeXus et décrits par un profil au-delà de 2²⁴ valeurs (environ 16,8 millions) sont prévisualisés avec un pas le long de chaque axe (les axes des images NeXus sont encore lus entièrement, pour les vérifier comme à l’import) ; les jeux de données composites et les signaux stockés dans des tableaux 2D utilisent encore des objets complets pour leurs aperçus graphiques

  • Les jeux de données à trois dimensions ou plus (piles d’images, cubes spectraux…) sont désormais listés dans le navigateur HDF5 et importés sous la forme d’une image ou d’un signal par trame : un sélecteur de vue choisit les axes affichés, les trames (première, dernière et pas selon un autre axe) et l’indice des autres axes, affiche la première trame en aperçu, et importe les trames une fois Importer ces trames coché (avec une confirmation au-delà de 100 trames). Les trames des jeux de données NeXus conservent leurs axes, et leur titre donne leur position (par exemple la position du moteur pour chaque image de détecteur d’un scan)

  • Les attributs de jeux de données de plus de 10 000 valeurs ne sont plus copiés dans les métadonnées des objets importés

Le guide de l’explorateur HDF5 décrit l’import d’objets scientifiques, l’origine expérimentale et les limites des aperçus.

Scripts, macros et plugins :

  • Un objet ou un groupe recherché par son titre, depuis une macro, un plugin, un client distant (par exemple get_object("My signal")) ou l’API Web, n’est plus silencieusement remplacé par le premier trouvé lorsque plusieurs objets ou groupes portent ce titre (par exemple des fichiers importés deux fois, des objets « Untitled ») : une erreur indique désormais les objets correspondants avec leur UUID, qui les identifie sans ambiguïté (HTTP 409 pour l’API Web)

  • Pour les développeurs de plugins : patch_title_with_ids ne prend plus de troisième argument (id_func), et les fonctions des anciens identifiants de type s001 (SHORT_ID_REGEX, find_by_short_id, find_short_ids_in_title, replace_short_ids_by_uuids_in_titles, replace_uuids_by_short_ids_in_titles) sont retirées de datalab.objectmodel, les titres désignant désormais les objets par leur UUID

  • Pour les développeurs de contrôleurs DataLab personnalisés dérivés de BaseProxy : les nouvelles méthodes export_capsule et open_capsule doivent être implémentées

🛠️ Corrections de bugs#

Performances avec de nombreux objets :

  • Correction du ralentissement progressif des traitements à mesure que les signaux ou les images s’accumulent dans un panneau : chaque nouveau résultat réécrivait les titres de tous les objets existants, reconstruisait toute l’arborescence des objets et mesurait de nouveau chaque titre, si bien que créer 1000 signaux l’un après l’autre prenait environ 39 minutes ; cela prend désormais environ 3 minutes (une étape de traitement avec 1000 objets dans le panneau est passée de 2,3 s à environ 0,3 s)

  • Les panneaux d’images ne ralentissent plus à cause des courbes de coupe conservées pour les images masquées (nécessite PlotPy ≥ 2.11.2)

  • Correction de l’altération des titres faisant référence à des objets numérotés 1000 ou plus (par exemple s1000) lors de l’ajout ou du réordonnancement d’objets

Disposition de la fenêtre :

  • Correction de la largeur des panneaux Signal/Image non restaurée au démarrage : après avoir réduit les panneaux puis redémarré DataLab, ils réapparaissaient plus larges (jusqu’à leur largeur maximale) au lieu de conserver la largeur choisie par l’utilisateur

  • Correction de l’échec du démarrage de DataLab lorsque son fichier de configuration contenait une disposition de fenêtre ou un nom de fichier journal invalide (par exemple après une modification manuelle du fichier) : ces paramètres sont désormais ignorés, et les paramètres par défaut sont utilisés

Console :

  • Correction de la console qui restait affichée en cas d’erreur après la désactivation de Afficher la console en cas d’erreur dans la boîte de dialogue des préférences (avec Qt 5, lorsque ce paramètre était activé au démarrage), jusqu’au redémarrage de DataLab

Démo :

  • Correction de l’échec de la démo, avec l’erreur « No module named “pytest” », dans la version autonome de DataLab (installée avec l’installeur MSI) et dans les installations sans les dépendances de test (par exemple pip install datalab-platform), qu’elle soit lancée depuis le menu ?, la page d’accueil, la dernière étape de la visite guidée ou la commande datalab-demo (corrige l’issue #365)

  • La commande datalab-demo ne supprime plus la configuration DataLab de l’utilisateur : la démo s’exécute désormais avec les paramètres par défaut, sans lire ni modifier les paramètres de l’utilisateur

Version autonome :

  • Correction de la version autonome de DataLab qui s’arrêtait avec un code de succès lorsqu’elle ne parvenait pas à démarrer : elle s’arrête désormais avec un code d’erreur, afin que les scripts et outils de déploiement qui la lancent puissent détecter l’échec (la cause est toujours écrite dans datalab_error.log, dans le dossier courant)

Mise à l’échelle de l’affichage :

  • Correction du flou de l’écran de démarrage, du logo DataLab de la page d’accueil et de la visite guidée, et du filigrane des graphiques vides avec une mise à l’échelle de l’affichage Windows supérieure à 100 % (par exemple 125 %) : ils sont désormais affichés à la résolution de l’écran

  • Correction de la majeure partie du texte de l’interface (page d’accueil, propriétés des objets, onglets des panneaux, boîtes de dialogue, …) qui conservait sa taille à 100 % avec une mise à l’échelle de l’affichage Windows supérieure à 100 % (par exemple 125 %), alors que les menus et la barre d’état étaient agrandis. Tout le texte suit désormais la mise à l’échelle de l’affichage et le réglage de la taille du texte de Windows, et utilise la police standard des applications Windows (« Segoe UI »). Cela concernait DataLab exécuté avec Qt 5, comme l’application autonome (nécessite guidata ≥ 3.16.1)

  • Correction de la ligne de l’axe des X des graphiques de signaux et d’images, qui n’était pas tracée avec une mise à l’échelle de l’affichage de 125 % ou 150 % par exemple, selon la taille et la position du graphique dans la fenêtre (nécessite PythonQwt ≥ 0.17.1)

  • Correction des images affichées avec une résolution inférieure à celle de l’écran avec une mise à l’échelle de l’affichage supérieure à 100 % : avec une mise à l’échelle de 200 %, les images étaient affichées avec la moitié de la résolution de l’écran, et avec 125 %, une ligne et une colonne de pixels de l’écran sur cinq étaient dupliquées, ce qui rendait irréguliers les détails fins (par exemple le bruit). Les images sont désormais affichées à la résolution de l’écran (nécessite PlotPy ≥ 2.12.1)

  • Correction de l’icône rouge des plugins dans la barre d’état (affichée lorsque des plugins n’ont pas pu être chargés), qui était trop petite et décalée vers le coin supérieur gauche avec une mise à l’échelle de l’affichage supérieure à 100 % (par exemple réduite de moitié avec 200 %)

Thème sombre :

  • Correction de la plupart des fenêtres qui conservaient une barre de titre blanche avec le thème sombre sous Windows, à côté de leur contenu sombre : l’historique des conversations de l’Assistant IA, la capsule d’espace de travail, la palette de commandes et d’autres boîtes de dialogue, l’assistant d’importation, les boîtes de confirmation et de saisie (par exemple lors du renommage d’un groupe ou d’une conversation) et les panneaux détachés de la fenêtre principale (vues signal et image, panneaux macro, historique, Assistant IA et accueil, console). Toutes les fenêtres ont désormais une barre de titre sombre avec le thème sombre, y compris après un changement du mode de couleur dans la boîte de dialogue des préférences (nécessite guidata ≥ 3.17.2, corrige Issue #490)

Filigrane des graphiques :

  • Correction du filigrane des graphiques vides, qui était lu dans une autre installation de DataLab partageant la même configuration utilisateur (par exemple DataLab installé dans un autre environnement Python) : le filigrane disparaissait une fois cette autre installation supprimée, et restait flou sur les écrans haute résolution lorsqu’il s’agissait d’une version plus ancienne. Le filigrane du DataLab en cours d’exécution est désormais toujours utilisé

Affichage des signaux :

  • Correction du sous-échantillonnage automatique des signaux (Préférences > Visualisation > Signaux), qui ne commençait qu’au-delà de 5 fois le nombre maximal de points configuré : avec la valeur par défaut de 100 000 points, les signaux de quelques centaines de milliers de points étaient tracés en entier, ce qui ralentissait l’affichage. Les signaux comportant plus de points que ce maximum sont désormais sous-échantillonnés de sorte qu’au plus ce nombre de points soit tracé, et la boîte de dialogue des préférences ainsi que la documentation indiquent désormais la valeur par défaut réelle (100 000 au lieu de 10 000) (corrige Issue #455)

  • Correction des modifications des préférences de sous-échantillonnage automatique et d’épaisseur de trait qui ne s’appliquaient qu’aux courbes des signaux sélectionnés : les autres courbes conservaient les anciennes préférences, même une fois sélectionnées à nouveau. Ces préférences s’appliquent désormais à toutes les courbes dès la fermeture de la boîte de dialogue des préférences

  • Correction des graduations de l’axe X qui étaient décalées par rapport aux lignes verticales de la grille et aux courbes après l’ouverture d’un signal ou un changement de sélection, pour les signaux dont l’axe X ne commence et ne se termine pas sur une graduation (par exemple, step.npy des données de test de Sigima) : le décalage persistait jusqu’à un déplacement ou un zoom de la vue. L’axe X reste désormais aligné avec la grille et les courbes (corrige Issue #457)

  • Correction des courbes des espaces de travail rechargés qui conservaient l’épaisseur de trait qu’elles avaient lors de l’enregistrement de l’espace de travail : les modifications de la préférence d’épaisseur de trait (Préférences > Visualisation > Signaux) ne s’y appliquaient plus, et les traits épais n’étaient plus tracés avec une largeur de 1 pixel pour les signaux comportant de nombreux points, ce qui ralentissait leur affichage. Seules les épaisseurs de trait choisies pour une courbe (par exemple dans sa boîte de dialogue de paramètres) sont désormais enregistrées, et elles sont elles aussi tracées avec une largeur de 1 pixel pour les signaux comportant de nombreux points. À l’ouverture des espaces de travail et des fichiers d’historique enregistrés avec DataLab 1.3 ou antérieur, qui enregistraient l’épaisseur de trait de chaque courbe, les épaisseurs de trait de 1 sont supprimées afin que les courbes suivent la préférence d’épaisseur de trait ; les autres épaisseurs de trait sont conservées

Palettes de couleurs personnalisées :

  • Correction des palettes de couleurs personnalisées (créées avec le gestionnaire de palettes de couleurs) qui étaient enregistrées en dehors du répertoire de configuration de DataLab, dans un répertoire .plotpy ou .none du répertoire de configuration de l’utilisateur partagé avec les autres applications basées sur PlotPy, selon la manière dont DataLab avait été lancé. Elles sont désormais enregistrées dans le sous-répertoire plotpy du répertoire de configuration de DataLab ; la première fois, les palettes de couleurs personnalisées enregistrées dans les anciens répertoires y sont copiées (nécessite PlotPy ≥ 2.12.0)

Import HDF5 :

  • Correction de l’écrêtage des images contenant des valeurs entières non signées sur 32 bits supérieures à 2 147 483 647 lors de leur import depuis un fichier HDF5 (avertissement « Clipping uint32 data to int32 ») : ces images sont désormais importées en flottants sur 64 bits en conservant chaque valeur exactement. Les autres images entières qu’aucun type entier pris en charge ne peut contenir utilisent aussi, lorsque c’est possible, un type flottant suffisamment précis, au lieu d’être arrondies en flottants sur 32 bits au-delà de 16 777 216 ; un avertissement est émis lorsqu’aucun type pris en charge ne garantit une conversion exacte (notamment au-delà de ±2⁵³ pour float64)

  • Correction de la perte de la partie imaginaire des jeux de données 1D complexes en simple précision (complex64) lors de leur import depuis un fichier HDF5 : ils sont désormais importés comme des signaux complexes. Les signaux entiers au-delà de ±2⁵³ émettent désormais aussi l’avertissement de précision au lieu d’être arrondis silencieusement

  • Correction de l’import de plusieurs jeux de données depuis des fichiers HDF5, qui s’arrêtait au premier jeu de données impossible à importer : les autres jeux de données sont désormais importés, et ceux qui n’ont pas pu l’être sont listés dans un message unique à la fin

  • Correction de l’échec d’ouverture dans l’explorateur HDF5 des fichiers HDF5 contenant des liens rompus, par exemple les fichiers maîtres de synchrotron dont les fichiers de détecteur ne sont pas disponibles (liens externes vers un fichier absent) : les liens rompus sont désormais ignorés et le reste du fichier peut être exploré et importé

  • Correction des fichiers HDF5 contenant un groupe lié dans lui-même ou dans l’un de ses sous-groupes, qui ne pouvaient pas être ouverts dans l’explorateur HDF5 (le fichier était parcouru sans fin jusqu’à une erreur) : ces liens vers un groupe parent sont désormais ignorés, tandis que les autres alias d’un groupe ou d’un jeu de données restent affichés à chacun de leurs chemins

  • Correction des jeux de données stockés dans d’autres fichiers, comme les données de détecteur des fichiers maîtres de synchrotron, qui n’apparaissaient pas dans l’explorateur HDF5 même lorsque ces fichiers sont disponibles : les jeux de données atteints par un lien externe étaient recherchés à leur chemin dans leur propre fichier, si bien qu’ils étaient ignorés, ou que les données d’un autre jeu de données du fichier ouvert, situé à ce chemin, étaient importées à leur place. Ils sont désormais listés et importés à leur chemin dans le fichier ouvert

  • Correction de l’échec d’ouverture des fichiers HDF5 dont le nom contient une virgule : la virgule était prise pour le séparateur entre un nom de fichier et le nom d’un jeu de données à importer. Lors de l’ajout d’un tel espace de travail, la question proposant de vider l’espace de travail n’indiquait pas non plus que sa provenance n’est pas importée, et un ajout annulé par l’utilisateur était tout de même enregistré dans le panneau Historique

  • Correction des jeux de données contenant une seule ligne de valeurs (par exemple, un scan unique stocké sous forme de tableau 1 × N), qui étaient ignorés sans message lors de leur import depuis un fichier HDF5 : ils sont désormais importés et prévisualisés comme des signaux

  • Correction d’une erreur lors d’un clic sur Afficher le tableau dans l’explorateur HDF5 après la sélection d’un groupe au clavier, ou après la fermeture du fichier du jeu de données sélectionné : le bouton n’affiche désormais que des tableaux, et il est désactivé une fois le fichier fermé

Enregistrement de l’espace de travail :

  • Correction d’un enregistrement en échec qui détruisait la version précédente du fichier d’espace de travail : le fichier était vidé avant l’écriture des données, si bien qu’une erreur pendant l’enregistrement, un disque plein ou une interruption ne laissaient sur le disque ni l’ancien ni le nouvel espace de travail. Les espaces de travail, les capsules et les fichiers d’historique (.dlhist) sont désormais écrits dans un fichier temporaire, qui ne remplace le fichier précédent qu’une fois entièrement écrit ; en cas d’échec de l’enregistrement, le fichier précédent reste intact

Import de fichiers :

  • Correction de l’ouverture des fichiers TIFF compressés (compression LZW, JPEG ou WebP), qui échouait avec l’erreur « requires the “imagecodecs” package » ; LZW est la compression par défaut de nombreux outils d’acquisition et d’édition d’images. Ces fichiers s’ouvrent désormais sans installation supplémentaire, y compris avec l’installeur autonome. Les images binaires compressées en CCITT sont également prises en charge avec l’installeur autonome et avec Python 3.11 ou ultérieur (corrige l’issue #381)

Métadonnées :

  • L’ajout, le collage ou la suppression de métadonnées marque désormais l’espace de travail comme modifié : DataLab propose donc d’enregistrer ces changements avant de se fermer

  • L’import de métadonnées depuis un fichier dans un objet (Édition > Métadonnées > Importer les métadonnées) ne lui donne plus l’identité de l’objet dont les métadonnées avaient été exportées : deux objets partageant une identité perturbaient les références aux sources dans les titres, Sélectionner les objets source et l’enregistrement de l’espace de travail

Régions d’intérêt :

  • Correction de la perte de l’option Inverser la logique de la ROI des ROI d’image lors de la validation de l’éditeur de ROI : l’option restait sans effet lorsqu’elle était définie dans la boîte de dialogue de coordonnées de l’éditeur (par exemple ROI rectangulaire), et les ROI d’image créées avec cette option (par exemple par une macro) la perdaient une fois modifiées

  • Correction des ROI définies en indices de pixels (par exemple par une macro ou par le contrôle à distance), qui étaient converties en coordonnées physiques lors de la validation de l’éditeur de ROI. Elles restent désormais en indices de pixels, y compris lorsqu’elles sont déplacées dans l’éditeur

Traitements :

  • Les résultats de l’extraction de plusieurs régions d’intérêt dans un seul objet peuvent de nouveau être retraités : l’onglet Traitement affichait « Unknown computing feature: extract_rois » avec Réappliquer désactivé, et le rejeu de l’historique ignorait l’action

  • Édition > Retraiter recalcule désormais aussi les résultats des opérations combinant plusieurs objets (par exemple la différence de deux signaux ou la moyenne de plusieurs images), qui étaient ignorés

  • Correction du Traitement > Rééchantillonnage des images, qui décalait toutes les valeurs d’un demi-pixel : rééchantillonner une image avec les paramètres par défaut, c’est-à-dire sur sa propre grille, remplissait sa dernière ligne et sa dernière colonne de NaN. Les paramètres X/Y min/max sont désormais les coordonnées des centres du premier et du dernier pixel de sortie (par défaut, ceux de l’image), et le mode “Taille de pixel” conserve exactement la taille de pixel demandée

  • Correction de la somme, de la moyenne, du produit et de l’écart-type de plusieurs signaux, ainsi que de leur combinaison en image, qui dépendaient de l’ordre des signaux : lorsqu’un signal réel venait en premier, les parties imaginaires des signaux complexes étaient perdues

  • La somme, la moyenne et le produit de plusieurs images acceptent désormais les images complexes, qui provoquaient une erreur

  • Correction du Traitement > Rééchantillonnage des images complexes avec les paramètres par défaut, et de l”Étalonnage polynomial de l’axe Z des images complexes, qui supprimaient les parties imaginaires : les images complexes restent désormais complexes

  • Correction de la modification en place du résultat d’un retournement diagonal, horizontal ou vertical ou d’une rotation de 90° d’une image (par exemple depuis une macro ou un plugin), qui modifiait aussi l’image source

  • Correction de l’extraction de plusieurs régions d’intérêt dans une seule image, qui donnait des coordonnées erronées aux images à coordonnées non uniformes (les coordonnées X étaient prises sur les lignes extraites et les coordonnées Y sur les colonnes extraites)

  • La rotation arbitraire des images (Traitement > Géométrie > Rotation de…) refuse désormais les images à coordonnées non uniformes, comme le redimensionnement et le rééchantillonnage, au lieu de produire une image dont les coordonnées ne correspondaient pas à ses pixels

  • Correction de l’incertitude du produit de signaux, qui était perdue là où l’un des signaux est nul : elle y est désormais également propagée

  • Correction du décalage d’un pixel des ROI, des annotations et des résultats d’analyse (centroïdes, pics détectés, contours…) après une symétrie ou une rotation de 90° d’une image ; après une rotation de 90° d’une image non carrée, ou d’une image dont les coordonnées ne commencent pas à zéro, les résultats d’analyse se retrouvaient même loin des éléments qu’ils décrivent. Ils se déplacent désormais exactement avec les pixels ; pour les images à coordonnées non uniformes, les cercles, ellipses et polygones sont déplacés de façon approchée lorsque les pixels sont inversés le long d’un axe non uniforme (un cercle ne reste pas un cercle). Les ROI définies en indices de pixels sont aussi correctement déplacées, et les ROI inverses (qui masquent l’intérieur de leur forme) ne deviennent plus des ROI normales après ces opérations, une translation ou une distribution d’images sur une grille

  • Correction de ROI > Extraire…, qui donnait à l’image extraite une origine erronée lorsque les coordonnées de l’image source ne commencent pas à zéro, et des coordonnées ne correspondant pas aux pixels extraits pour les images à coordonnées non uniformes

  • Correction des coordonnées des résultats d’analyse calculés dans une ROI, qui pouvaient être fausses jusqu’à un demi-pixel

  • Correction des résultats d’analyse des images à coordonnées non uniformes (Analyse > Barycentre…, Centre du cercle minimum…, Détection de pics 2D, Détection de contours…, Transformée de Hough circulaire… et Détection de taches), qui étaient donnés en indices de pixels, ou selon l’ancienne taille de pixel et l’ancienne origine d’une image passée en coordonnées non uniformes, de sorte qu’ils étaient tracés loin des éléments qu’ils décrivent : ils sont désormais placés aux positions des pixels sur les axes de l’image, les rayons étant mis à l’échelle de la taille locale des pixels. Les résultats des images à coordonnées uniformes sont inchangés

  • ROI > Extraire… signale désormais une erreur explicite pour une région d’intérêt ne contenant aucun pixel de l’image (par exemple une cellule d’une grille de ROI plus étroite qu’un pixel, ou une région hors de l’image) au lieu de créer silencieusement une image vide ; les autres régions d’intérêt sont tout de même extraites

  • Correction de Traitement > Ajustement de niveau > Soustraction d’offset, qui utilisait une zone de fond tronquée à des coordonnées entières : la zone était erronée pour les images dont les coordonnées ne sont pas en pixels (par exemple en millimètres), et vide lorsqu’elle mesurait moins d’une unité

Plugins :

  • Les plugins organisés en dossier, comme ceux créés par datalab-plugin create --project, sont désormais chargés lorsque leur dossier est ajouté aux répertoires de plugins, sans devoir être installés au préalable : ils étaient ignorés sans message, sauf si une installation antérieure avait laissé des informations de paquet dans le projet. Le dossier du projet lui-même peut désormais être ajouté, au lieu de son sous-dossier src (corrige l’issue #411)

  • Correction de petites fenêtres vides qui apparaissaient brièvement à l’écran à l’ouverture de Plugins > Configurer les plugins…, juste avant l’affichage de la boîte de dialogue (corrige l’issue #486)

Plugins et historique :

  • Le rejeu d’une action de l’historique ou le recalcul d’un résultat créé par une fonctionnalité de plugin portant le même nom qu’une fonctionnalité intégrée exécute désormais la fonctionnalité du plugin au lieu de la fonctionnalité intégrée

Panneau d’historique :

  • Correction d’un avertissement démesuré qui s’affichait lors de la suppression d’un groupe de signaux ou d’images dont les résultats de traitement étaient conservés dans un autre groupe, même lorsque le panneau d’historique n’enregistrait pas : il listait chaque objet supprimé, souvent sous la forme d’un identifiant illisible, et indiquait que des « opérations n’avaient pas pu être reconnectées » alors qu’il n’y avait rien à reconnecter. La suppression de tels objets n’affiche plus aucun message, et les résultats qui en dépendent restent inchangés, comme auparavant. L’avertissement n’est désormais affiché que lorsqu’une étape de traitement enregistrée perd sa source, et il liste chaque étape une seule fois, dans un message de taille limitée (corrige l’issue #451)

  • Correction de la colonne Description du panneau d’historique qui affichait le contenu brut des paramètres volumineux, par exemple l’histogramme complet d’une action Luminosité et contraste : la ligne prenait une hauteur démesurée et le défilement du panneau devenait erratique. La description affiche désormais les paramètres réels (par exemple le minimum et le maximum de la plage de luminosité et de contraste) sur une seule ligne, raccourcie à la largeur de la colonne, le résumé complet figurant dans son info-bulle ; les valeurs longues sont raccourcies, et les détails dépliés défilent dans une ligne de hauteur limitée (corrige l’issue #369)

Titres des objets :

  • Correction des légendes des graphiques qui affichaient toujours le titre généré d’origine après le renommage d’un objet, par exemple un profil extrait d’une image (corrige Issue #323)

  • Correction des références aux sources illisibles dans les titres lorsque l’objet est sélectionné dans l’arborescence signal ou image, notamment sous Linux (corrige Issue #358)

  • Correction des titres de résultats qui désignaient de mauvais objets sources après l’ajout d’un espace de travail HDF5 à une session non vide ; ajouter deux fois le même espace de travail conserve désormais aussi des chaînes de traitement importées indépendantes, de sorte que Retraiter et Sélectionner les objets source utilisent les sources issues du même import (corrige Issue #357)

Ajustement de courbes :

  • Correction de l’ajustement planckien automatique (Traitement > Ajustement > Ajustement planckien), qui renvoyait une courbe environ 150 fois plus basse que le signal sur des données en unités physiques, comme un signal de corps noir avec des longueurs d’onde en mètres ; la fenêtre d’ajustement planckien interactif part également d’une courbe correspondant au pic du signal (corrige l’issue #400)

  • Correction de l’ajustement exponentiel, qui échouait sur des constantes de temps courtes selon l’unité de X, par exemple une constante de temps de 1 ms avec X en secondes (ajustements automatique et interactif)

Création de signaux :

  • Le signal de corps noir (Création > Corps noir (loi de Planck)) a désormais des titres et des unités d’axes (longueur d’onde en m, luminance énergétique spectrale en W·sr⁻¹·m⁻³), qui étaient absents (corrige l’issue #400)

Contrôle à distance :

  • Correction des fichiers chargés à distance avec load_from_files ou load_from_directory qui étaient parfois ignorés silencieusement, ou encore en cours de chargement après le retour de l’appel, lorsqu’ils étaient demandés juste après le démarrage de DataLab : les requêtes reçues pendant le démarrage de DataLab sont désormais traitées dès que sa fenêtre principale est prête (corrige l’issue #398)

  • Les erreurs levées par les commandes à distance, comme calc avec une fonction de calcul inconnue ou set_object avec un objet inconnu, sont désormais signalées au client au lieu d’être ignorées silencieusement

  • Correction des commandes à distance qui renvoyaient parfois le résultat de la commande précédente au lieu du leur : par exemple, get_current_object_uuid pouvait renvoyer un nom de panneau au lieu de None en l’absence d’objet courant

  • Correction du blocage de DataLab lorsqu’il était fermé alors qu’une commande à distance était encore en cours d’exécution (par exemple en fermant la fenêtre principale avec call_method("close"))

  • Correction du plantage de DataLab, ou de l’ouverture d’une boîte de message d’erreur, lorsqu’une requête d’un client distant ou d’une macro échouait, par exemple un calcul demandé avec calc qui échouait sur le signal sélectionné, ou un fichier qui ne pouvait pas être lu avec load_from_files : le client n’était pas informé de l’erreur, et DataLab plantait lorsqu’il s’exécutait sans affichage (par exemple en arrière-plan, pour des tests ou de l’automatisation). L’erreur est désormais signalée au client, sous la forme d’une xmlrpc.client.Fault avec XML-RPC ou d’une erreur HTTP avec l’API Web (500 pour un calcul en échec, 404 pour une fonction de calcul inconnue), et affichée dans la barre d’état de DataLab ; cela s’applique aussi aux jeux de données d’un fichier HDF5 qui n’ont pas pu être importés. Les macros et les clients distants reçoivent désormais une exception là où ils poursuivaient leur exécution après la fermeture de la boîte de message (corrige l’issue #404)

  • Correction de l’échec de toutes les requêtes de l’API Web au bout de 30 secondes, avec une erreur HTTP 500 (« Main thread execution timed out »), lorsque le serveur de l’API Web avait été démarré par un client distant avec start_webapi_server (XML-RPC), y compris pour les requêtes qui auraient dû échouer immédiatement, comme calc avec une fonction de calcul inconnue ; l’opération demandée pouvait même être effectuée plus tard, après le renvoi de l’erreur. Les requêtes sont désormais servies comme lorsque le serveur est démarré depuis le menu Fichier > API Web (corrige l’issue #403)

  • Correction des images à coordonnées non uniformes qui perdaient celles-ci lors d’un transfert par l’API Web (GET et PUT /objects/{name}/data) : elles étaient reconstruites avec des coordonnées uniformes par défaut. Le format de données NPZ inclut désormais ces coordonnées ; les archives écrites par les versions antérieures restent lisibles. Les clients disposant de leur propre lecteur NPZ, comme DataLab-Kernel, doivent prendre en charge les nouvelles entrées pour en bénéficier

Assistant IA :

  • Correction de l’absence du lien Enregistrer dans les macros lorsqu’une conversation est rouverte depuis Historique… : une macro proposée par l’assistant lors d’une session précédente ne pouvait plus être enregistrée. Les conversations rouvertes affichaient aussi tous les appels d’outils comme réussis, y compris ceux en échec ; elles affichent désormais leur résultat réel (corrige l’issue #447)

  • L’enregistrement d’une macro proposée par l’assistant propose désormais un lien Afficher dans le panneau de macros : le panneau de macros étant regroupé en onglets avec l’assistant IA, la macro enregistrée restait cachée derrière la conversation

  • Correction de l’assistant qui répondait à une demande d”écriture de macro en plaçant le code dans sa réponse, d’où il ne pouvait pas être enregistré dans le panneau de macros : il propose désormais la macro sans l’exécuter (la boîte de dialogue de confirmation indique qu’elle ne sera pas exécutée) et offre le lien Enregistrer dans les macros. Un lien Enregistrer dans les macros est également proposé sous chaque bloc de code Python de ses réponses, sauf si la création de macros est désactivée

Sécurité :

  • Ouvrir un espace de travail reçu d’une autre personne ne permet plus de faire charger ou exécuter par DataLab un autre code installé sur l’ordinateur. Les paramètres enregistrés avec les objets, les résultats d’analyse et les actions de l’historique nomment leur classe, et DataLab importait le module ainsi nommé puis appelait l’objet désigné, ce qu’un fichier modifié pouvait exploiter, par exemple pour faire quitter DataLab. Seules les classes de paramètres de DataLab, Sigima, guidata et des plugins installés sont désormais utilisées ; les autres paramètres enregistrés sont signalés comme illisibles (corrige l’issue #407)
