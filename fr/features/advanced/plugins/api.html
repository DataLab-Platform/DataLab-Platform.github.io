API publique#

Cette page est la référence des classes et fonctions à la disposition des plugins. Voir Développer des plugins pour leur utilisation, et Plugins d’application pour les déclarations des plugins d’application.

Système de plugins de DataLab#

Le système de plugins de DataLab fournit un moyen d’étendre l’application avec de nouvelles fonctionnalités.

Les plugins sont des modules Python qui reposent sur deux classes :

  • PluginInfo, qui stocke des informations sur le plugin

  • PluginBase, qui est la classe de base pour tous les plugins

Les plugins peuvent également étendre les fonctionnalités d’entrée/sortie de DataLab en fournissant de nouveaux formats d’image ou de signal. Pour ce faire, ils doivent fournir une sous-classe de ImageFormatBase ou SignalFormatBase, dans laquelle les informations de format sont définies à l’aide de la classe FormatInfo.

datalab.plugins.discover_plugins() → list[ModuleType][source]#

Découvrir les plugins via les points d’entrée de packages et la convention de nommage.

Les packages installés peuvent exposer une sous-classe de PluginBase via le groupe de points d’entrée datalab.plugins. Cette fonction recharge ou importe également les modules et packages qui respectent la convention de nommage historique "{MOD_NAME}_*", ainsi que le module adapters.desktop de ces packages, qui définit la classe du plugin des packages organisés comme ceux créés par datalab-plugin create.

Les erreurs d’importation pour les plugins individuels sont capturées et enregistrées afin qu’un plugin défectueux n’empêche pas les autres de se charger. Les traces d’erreurs sont accumulées dans les attributs de classe PluginRegistry afin que les appelants (par exemple, la fenêtre principale) puissent les rejouer dans la console interne une fois qu’elle est prête.

Cette fonction modifie sys.modules et le registre des plugins sans synchronisation : ne l’appelez que depuis le thread principal Qt.

Renvoie:

Modules importés ou rechargés contenant les plugins découverts

datalab.plugins.reload_plugin_modules() → None[source]#

Recharger les modules de plugins et réinitialiser les classes de plugins.

Cet assistant est destiné au rechargement à chaud des plugins à l’exécution. Il :

  • Met à jour le chemin de recherche des plugins

  • Efface le registre des classes de plugins

  • Recharge ou importe tous les modules correspondant à la convention de nommage des plugins

Comme discover_plugins(), cette fonction n’est pas thread-safe : ne l’appelez que depuis le thread principal Qt.

datalab.plugins.PLUGIN_ENTRY_POINT_GROUP est le groupe de points d’entrée des classes de plugins de DataLab Desktop ("datalab.plugins") ; les classes de plugins de DataLab-Web utilisent le groupe datalab.web_plugins (voir Plugins et DataLab-Web). Les autres noms exportés par datalab.plugins, tels que PluginRegistry ou discover_plugins, sont utilisés par DataLab pour charger et gérer les plugins, et ne sont pas décrits ici.

class datalab.plugins.recipes.RecipeDescriptor(recipe_id: str, plugin_version: str, title: str, version: str, run: Callable[[Mapping[str, tuple[SignalObj | ImageObj, ...]], DataSet | None, RecipeExecutionContext], RecipeOutcome], description: str = '', inputs: Sequence[RecipeInputSlot] = (), parameter_class: type[DataSet] | None = None, suggest_bindings: Callable[[tuple[SignalObj | ImageObj, ...]], Mapping[str, Sequence[SignalObj | ImageObj]]] | None = None, check_inputs: Callable[[Mapping[str, tuple[SignalObj | ImageObj, ...]], DataSet | None], Sequence[RecipeDiagnostic]] | None = None)[source]#

Déclaration typée et versionnée d’une recette sans interface graphique fournie par un plugin.

L’absence de parameter_class déclare une recette sans paramètre dont la fonction d’exécution reçoit None comme second argument. Dans le cas contraire, cet argument doit être une instance de la sous-classe DataSet déclarée.

suggest_bindings reçoit les objets candidats et renvoie une proposition d’affectation de certains d’entre eux aux emplacements d’entrée (par exemple à partir des métadonnées). Les hôtes l’utilisent pour affecter les entrées sans interroger l’utilisateur.

check_inputs reçoit des entrées complètes et les paramètres (ceux par défaut lors de l’évaluation d’une sélection) et renvoie des diagnostics : les erreurs bloquent l’exécution, les avertissements sont affichés. class datalab.plugins.recipes.RecipeRunRecord(run_id: str, plugin_id: str, plugin_version: str, recipe_id: str, recipe_version: str, parameters_json: str, input_uuids: Mapping[str, Sequence[str]], output_uuids: Mapping[str, str], datalab_version: str, sigima_version: str, status: RecipeRunStatus, started_at: str, finished_at: str, schema_version: int = 1)[source]#

Provenance locale versionnée partagée par toutes les sorties d’une exécution de recette.

L’enregistrement est conservé sous forme de métadonnées JSON (voir to_dict()) dans l’option de métadonnées RECIPE_RUN_RECORD_OPTION de chaque objet de sortie, afin que les consommateurs externes (DataLab-Web, espaces de travail HDF5, outils) puissent s’appuyer sur le schéma suivant (version 1) :

  • schema_version (int) : toujours RECIPE_RUN_RECORD_SCHEMA_VERSION

  • run_id (str) : UUID partagé par toutes les sorties d’un même appel de recette

  • plugin_id / plugin_version (str) : plugin propriétaire et sa version

  • recipe_id / recipe_version (str) : recette (<plugin_id>:<name>) et version de son contrat

  • parameters_json (str) : DataSet guidata sérialisé avec dataset_to_json ("null" pour les recettes sans paramètre)

  • input_uuids (dict[str, list[str]]) : UUID des objets consommés par emplacement d’entrée — un dictionnaire (et non une liste à plat) afin que les rôles des emplacements soient conservés lors des allers-retours

  • output_uuids (dict[str, str]) : UUID de l’objet produit pour chaque identifiant de sortie

  • datalab_version / sigima_version (str) : versions de l’environnement

  • status (str) : une valeur de RecipeRunStatus

  • started_at / finished_at (str) : ISO 8601 avec fuseau horaire

Politique de compatibilité : les lecteurs doivent rejeter les enregistrements dont ils ne connaissent pas la schema_version (comme le fait from_dict()) ; tout ajout, suppression ou changement sémantique de champ impose d’incrémenter RECIPE_RUN_RECORD_SCHEMA_VERSION et de fournir un chemin de migration explicite pour les espaces de travail enregistrés.

class datalab.plugins.instruments.PluginInstrument(settings: DataSet)[source]#

Instrument ouvert par un outil de plugin.

DataLab écrit les valeurs modifiées dans settings avant d’appeler preview() ou acquire(). Les deux méthodes lèvent ValueError avec un message destiné à l’utilisateur lorsque les réglages ne peuvent pas être utilisés. Le plugin conserve une instance par outil pendant la session : les réglages sont ainsi conservés d’une ouverture à l’autre.

DataLab appelle open() à l’ouverture de la fenêtre de l’instrument et close() à sa fermeture (y compris lorsque le plugin est rechargé ou que DataLab se ferme). Il appelle ces méthodes, preview() et acquire() une à la fois, en dehors du fil d’exécution de l’interface graphique, même lorsque la fenêtre est fermée puis rouverte pendant un appel, et ne modifie settings qu’entre deux appels : un instrument lent ne fige pas DataLab. Les données reçues par l’instrument dans ses propres fils d’exécution (par exemple les événements d’un appareil) doivent être conservées jusqu’au prochain appel de preview() ou acquire().

Paramètres:

settings – réglages de l’instrument, modifiés par DataLab
