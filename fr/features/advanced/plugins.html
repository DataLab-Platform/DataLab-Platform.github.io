Plugins#

DataLab prend en charge une architecture de plugin robuste, permettant aux utilisateurs d’étendre les fonctionnalités de l’application sans modifier son noyau. Les plugins peuvent introduire de nouveaux outils de traitement, des formats d’importation/exportation de données ou des éléments d’interface graphique personnalisés, le tout intégré de manière transparente dans la plateforme.

Qu’est-ce qu’un plugin ?#

Un plugin est du code Python qui est automatiquement chargé par DataLab au démarrage. Il peut définir de nouvelles fonctionnalités ou modifier des fonctionnalités existantes.

Un plugin définit une classe qui hérite de datalab.plugins.PluginBase, comporte un attribut de classe nommé PLUGIN_INFO (une instance de datalab.plugins.PluginInfo) et implémente la méthode create_actions. DataLab trouve cette classe dans un répertoire de plugins (voir Où est positionné un plugin ?), sous l’une de ces deux formes :

  • Un fichier unique dont le nom commence par datalab_ (par exemple datalab_myplugin.py) et qui contient la classe. C’est la forme la plus simple, recommandée pour débuter : datalab-plugin create crée un tel fichier, prêt à l’emploi (voir Créer un plugin avec datalab-plugin create).

  • Un dossier dont le nom commence par datalab_ et qui contient un fichier __init__.py (un paquet Python, par exemple datalab_myplugin/). DataLab charge le dossier, puis son fichier adapters/desktop.py s’il existe : c’est là que les projets créés par datalab-plugin create --project définissent la classe (voir Créer un projet de plugin structuré en couches). Sinon, la classe est définie dans __init__.py.

Rien n’a besoin d’être installé : le fichier ou le dossier est chargé tel quel.

Les plugins distribués sous forme de paquets Python installés, comme les wheels du catalogue de plugins, déclarent leur sous-classe de PluginBase via le groupe de points d’entrée datalab.plugins, sans dépendre du préfixe datalab_. Un plugin trouvé des deux façons, par exemple un projet installé dont le dossier est aussi un répertoire de plugins, n’est chargé qu’une seule fois.

L’objet PLUGIN_INFO doit définir un id unique, préfixé par un espace de noms, qui reste stable lorsque le nom affiché ou la classe d’implémentation changent. DataLab utilise cet identifiant pour l’enregistrement et pour les paramètres d’activation persistants. Les plugins sans identifiant restent pris en charge grâce à un repli fondé sur le module et la classe, pour assurer la rétrocompatibilité, mais les nouveaux plugins ne doivent pas s’appuyer sur ce repli.

from datalab.plugins import PluginCapability, PluginInfo

PLUGIN_INFO = PluginInfo(
  id="org.example.my-plugin",
  name="My Plugin",
  version="1.0.0",
  capabilities=(
    PluginCapability.APPLICATION,
    PluginCapability.PROCESSING,
  ),
)

capabilities déclare comment DataLab peut présenter et utiliser un plugin. Les valeurs prises en charge sont PROCESSING, IO, VISUALIZATION et APPLICATION. Un plugin peut combiner plusieurs valeurs ; les applications métier déclarent généralement APPLICATION avec PROCESSING. La boîte de dialogue de configuration des plugins affiche les capacités déclarées dans un ordre stable. Les plugins existants qui omettent ce champ restent valides et sont affichés sans libellé de capacité.

Note

Seuls les fichiers et dossiers dont les noms commencent par datalab_ sont analysés pour les plugins.

DataLab prend en charge trois catégories de plugins, chacune ayant son propre objectif et mécanisme d’enregistrement :

  • Plugins de traitement et de visualisation Ajoutent des actions personnalisées pour le traitement des signaux ou des images. Cela peut inclure de nouvelles fonctions de calcul, des outils de visualisation de données ou des boîtes de dialogue interactives. Intégré dans un sous-menu dédié du menu « Plugins ».

  • Plugins d’entrée/sortie Définissent de nouveaux formats de fichiers (lecture et/ou écriture) gérés de manière transparente par le framework d’entrée/sortie de DataLab. Ces plugins étendent la compatibilité avec des formats de données personnalisés ou tiers.

  • Plugins HDF5 Plugins spéciaux qui prennent en charge les fichiers HDF5 avec des structures d’arbre spécifiques au domaine. Ceux-ci permettent à DataLab d’interpréter des signaux ou des images organisés de manière non standard.

Organisation du code source et distribution#

L’organisation du code source, le format de distribution et les capacités fonctionnelles sont des notions indépendantes. Un plugin en fichier unique et un plugin organisé en paquet Python utilisent la même API datalab.plugins.PluginBase ; aucune de ces formes ne détermine s’il fournit des fonctions de traitement, d’entrée/sortie, de visualisation ou d’application.

  • Plugin en fichier unique : un module datalab_<nom>.py, facile à modifier et à partager sans projet de packaging. Cette forme historique est aussi celle produite par défaut par datalab-plugin create ; elle n’est pas obsolète.

  • Paquet ou projet : des modules Python et, éventuellement, des ressources, des tests et des métadonnées de packaging. datalab-plugin create --project propose une organisation en couches, pas une architecture obligatoire pour tous les plugins.

  • Distribution wheel : une archive .whl installable, contenant des métadonnées normalisées et des points d’entrée de plugins. Un wheel peut contenir un seul module ou un paquet plus important ; c’est un format de distribution, pas une catégorie fonctionnelle de plugin.

Les modules en fichier unique et les wheels peuvent être installés avec Installer depuis un fichier… ou distribués dans les catalogues en ligne et locaux. Les catalogues n’imposent pas le projet en couches généré par --project. Empaqueter un module unique en wheel reste possible, mais est facultatif pour Desktop.

Formes de développement et distribution#

Forme de développement

Chargement direct du code source

Distribution gérée

Fichier Python unique

datalab_<nom>.py dans un répertoire de plugins

Fichier .py brut, ou wheel facultatif

Paquet ou projet Python

Dossier du paquet, y compris l’organisation src d’un projet

Wheel contenant le paquet et ses ressources

Les deux formats gérés fonctionnent dans les catalogues locaux et en ligne de Desktop. La forme historique en fichier unique n’est pas une catégorie fonctionnelle distincte et son code source n’a pas besoin d’être modifié pour être référencé dans un catalogue. Une entrée dans un catalogue Desktop n’implique pas la prise en charge de DataLab-Web.

Un fichier source chargé directement reste dans son répertoire de développement. Un fichier installé par DataLab est copié dans son stockage utilisateur géré. Un plugin n’est pas une macro : un plugin enregistre des fonctions persistantes dans l’application, tandis qu’une macro est un script exécuté pour automatiser une tâche. La prise en charge de la forme historique en fichier unique n’implique pas celle des API obsolètes de DataLab v0.20.

Compatibilité avec l’aperçu interactif#

Note

Les fonctions paramétrées standard enregistrées avec register_1_to_1 peuvent utiliser l’aperçu interactif sans moteur de rendu personnalisé. Elles doivent retourner un SignalObj ou un ImageObj, être importables dans un processus démarré par spawn et accepter des copies sérialisables des sources et paramètres. L’aperçu utilise un processus privé et ne publie aucun résultat dans l’espace de travail. Il ne protège pas des effets externes sur les fichiers, le réseau ou d’autres ressources. Enregistrez les fonctions qui ne doivent pas être exécutées provisoirement avec preview_enabled=False. Les erreurs de sérialisation ou de calcul sont signalées dans l’aperçu ; le chemin normal via OK reste disponible. Les implémentations personnalisées de DataSet.edit non prises en charge et les backends alternatifs de guidata ne sont pas remplacés.

Le processus dédié à l’aperçu peut être réutilisé entre les boîtes de dialogue. Les fonctions des plugins ne doivent pas supposer qu’un nouvel interpréteur Python est créé pour chaque aperçu : l’état local des modules dans le processus peut persister jusqu’à ce qu’un aperçu en cours soit annulé, que les plugins soient rechargés ou que DataLab se ferme.

Où est positionné un plugin ?#

Les plugins sont automatiquement découverts au démarrage à partir de plusieurs emplacements :

  • Un paquet Python installé peut déclarer sa classe de plugin via le groupe standard de points d’entrée datalab.plugins :

    [project.entry-points."datalab.plugins"]
my-plugin = "my_plugin.plugin:MyPlugin"

    La cible doit être une sous-classe de datalab.plugins.PluginBase. Il s’agit du mécanisme de distribution recommandé pour les plugins installés avec pip.

  • Le répertoire des plugins utilisateur : Typiquement ~/.DataLab_v1/plugins sur Linux/macOS ou C:/Users/YourName/.DataLab_v1/plugins sur Windows.

  • Répertoires de plugins supplémentaires : Tout nombre de répertoires supplémentaires peuvent être déclarés depuis Plugins > Configurer les plugins…, dans l’onglet Avancé (voir Onglet Avancé). Ils sont enregistrés dans la configuration de DataLab et analysés à chaque démarrage.

  • Le répertoire de distribution autonome : Si vous utilisez une version gelée (autonome), le dossier plugins situé à côté de l’exécutable est analysé.

  • Les plugins installés : wheels et modules installés depuis Plugins > Configurer les plugins…, soit depuis un fichier dans l’onglet Depuis un fichier (voir Onglet Depuis un fichier), soit depuis un catalogue de plugins dans l’onglet Catalogue (voir Onglet Catalogue).

  • Le dossier interne datalab/plugins/builtin (non recommandé pour les plugins utilisateur) : Cet emplacement est réservé aux plugins intégrés ou fournis et ne doit pas être modifié manuellement.

  • Répertoires supplémentaires listés dans la variable d’environnement DATALAB_PLUGINS : Un ou plusieurs répertoires peuvent être spécifiés, séparés par le séparateur de chemin du système d’exploitation (; sous Windows, : sous Linux/macOS), selon la même convention que PYTHONPATH. Tous les répertoires listés sont ajoutés aux chemins de recherche des plugins au démarrage ; les chemins inexistants sont ignorés silencieusement (un avertissement est consigné dans le fichier journal). Exemples :

    # Linux/macOS
export DATALAB_PLUGINS="/opt/my_plugins:/home/alice/datalab_plugins"

    :: Windows
set DATALAB_PLUGINS=C:\my_plugins;D:\shared\datalab_plugins

    Les modifications apportées à cette variable ne sont prises en compte qu’au démarrage de DataLab.

Un répertoire de plugins peut aussi être le dossier d’un projet de plugin, comme ceux créés par datalab-plugin create --project : DataLab recherche alors aussi dans son sous-dossier src, qui contient le dossier datalab_* du plugin. Les paquets Python dont dépend le plugin doivent être disponibles dans l’environnement de DataLab.

Gestion des plugins dans DataLab#

Le menu Plugins propose deux actions dédiées :

  • Configurer les plugins… Ouvre la boîte de dialogue de configuration des plugins, organisée en quatre onglets : Installés, Catalogue, Depuis un fichier et Avancé. Le survol du titre d’un onglet décrit son contenu. La boîte de dialogue se rouvre avec la taille qu’elle avait à sa dernière fermeture.

  • Recharger les plugins Recharge les modules de plugins depuis le disque sans redémarrer DataLab.

Lorsque les plugins sont globalement activés, un simple clic gauche sur le libellé Plugins : de la barre de statut ouvre également la même boîte de dialogue de configuration. L’icône n’est pas cliquable ; le raccourci reste disponible lorsqu’aucun plugin n’est chargé ou que certains plugins n’ont pas pu être chargés.

Onglet Installés#

Cet onglet liste tous les plugins découverts avec leur icône, nom, version, description et chemin de fichier, ainsi que les plugins qui n’ont pas pu être importés. Pour chaque entrée :

  • une case à cocher individuelle active ou désactive le plugin,

  • Ouvrir le fichier ouvre la source du plugin dans votre éditeur,

  • Afficher dans le dossier révèle le fichier du plugin dans le gestionnaire de fichiers du système.

Une case à cocher Activer tous les plugins et une boîte combinée Filtrer (Tous les plugins, Plugins activés, Plugins désactivés, Plugins avec erreurs) facilitent la navigation dans une grande collection de plugins. Un indicateur Dernier chargement : … montre quand les plugins ont été chargés pour la dernière fois pendant la session en cours, et le bouton Appliquer et recharger les plugins applique les modifications sans quitter la boîte de dialogue.

Onglet Catalogue#

Cet onglet liste les plugins du catalogue de plugins DataLab et des catalogues locaux de plugins (voir Catalogues locaux de plugins), avec leur description, leur licence et un lien vers leur code source. Les plugins maintenus par l’équipe DataLab sont marqués Officiel ; les autres sont des plugins de la Communauté, maintenus par leurs auteurs, ou des plugins d’un Catalogue local, fournis par votre organisation (l’infobulle d’un tel plugin indique le dossier de son catalogue). Un champ de recherche filtre la liste.

Installer copie ou télécharge le wheel ou le module en fichier unique disponible pour Desktop et la version de Python utilisée, vérifie sa taille et son empreinte SHA-256, puis l’installe comme décrit dans Onglet Depuis un fichier, après confirmation. Les versions numérotées peuvent proposer Mettre à jour vers…. Pour un module sans version comparable, un contenu modifié propose plutôt Remplacer… ; une empreinte identique indique qu’il est déjà installé. Les plugins installés avec pip ou fournis par des répertoires sources non gérés sont identifiés, mais ne sont pas modifiés.

Les catalogues ne sont lus que lorsque l’onglet est affiché ou actualisé, ainsi que lorsque les dossiers des catalogues locaux changent. Un catalogue illisible, par exemple un partage réseau non connecté, est signalé sous le nombre de plugins sans masquer les plugins des autres catalogues. L’adresse du catalogue de plugins DataLab est l’option plugins_catalog_url du fichier de configuration de DataLab : elle peut désigner une copie privée du catalogue, ou être vidée pour le désactiver, par exemple sur des ordinateurs sans accès à Internet. Pour un catalogue stocké dans un dossier, y compris un dossier partagé sur le réseau, utilisez plutôt un catalogue local de plugins.

Catalogues locaux de plugins#

Un catalogue local de plugins est un dossier, généralement partagé sur le réseau (par exemple \\fileserver\datalab\plugins), à partir duquel une organisation diffuse ses propres plugins, ou les versions de plugins publics qu’elle a validées, sans les publier. Les catalogues locaux complètent le catalogue de plugins DataLab et sont prioritaires sur lui : lorsque plusieurs catalogues proposent le même plugin (même nom de distribution ou même identifiant de plugin), seul le premier est affiché, afin que les utilisateurs installent la version choisie par l’organisation. Si le catalogue de plugins DataLab retire un plugin ainsi masqué, l’onglet le signale.

Les catalogues locaux sont déclarés :

  • dans l’onglet Avancé (voir Onglet Avancé) : ces dossiers sont enregistrés dans la configuration de DataLab (option plugins_catalog_path_list) ;

  • par la variable d’environnement DATALAB_PLUGINS_CATALOG, par exemple pour configurer tous les ordinateurs d’une organisation : les dossiers sont séparés par le séparateur de chemins du système (; sous Windows, : sous Linux/macOS) et sont prioritaires sur les dossiers de la configuration. Contrairement à DATALAB_PLUGINS, les dossiers indisponibles au démarrage de DataLab ne sont pas ignorés : ils sont signalés dans l’onglet Catalogue, et utilisés dès qu’ils deviennent disponibles et que les catalogues sont actualisés.

:: Windows
set DATALAB_PLUGINS_CATALOG=\\fileserver\datalab\plugins;D:\approved_plugins

Un dossier de catalogue local contient :

  • des fichiers de plugins sans index : DataLab recherche les wheels en Python pur déclarant un point d’entrée datalab.plugins et les fichiers source nommés datalab_<nom>.py à la racine du dossier, sans parcourir les sous-dossiers. Les wheels sont regroupés par distribution et version ; chaque module constitue un fichier installable, même s’il déclare plusieurs classes de plugins. Les métadonnées des modules sont lues statiquement lorsque c’est possible ; un nom inconnu est remplacé par le nom du module et une version inconnue reste vide, avec un suivi par empreinte. Les fichiers invalides sont signalés. Copier un module modifié ou une nouvelle version d’un wheel suffit pour le proposer ;

  • soit un fichier catalog.json, au format du catalogue de plugins DataLab, dont les URL des versions sont relatives au dossier : seuls les plugins qu’il liste sont affichés. Il peut s’agir d’une copie du catalogue de plugins DataLab avec ses wheels, ou d’un catalogue construit à partir des wheels du dossier avec datalab-plugin catalog build, puis modifié pour donner un nom d’affichage aux plugins, les déprécier ou les révoquer (champs status et status_reason), ou retirer une version (champ yanked).

Quel que soit le catalogue, DataLab vérifie la taille et l’empreinte SHA-256 du fichier avant son installation, l’inspecte sans l’exécuter et demande confirmation ; la boîte de dialogue indique le dossier du catalogue comme source. Pour un module, la validité du nom importable, l’encodage Python et la syntaxe sont vérifiés, avec une taille maximale de 4 Mio. L’inspection n’importe pas le code et ne certifie pas son comportement. L’organisation responsable d’un catalogue partagé doit en contrôler le contenu et limiter les droits d’écriture.

La commande datalab-plugin gère le fichier catalog.json d’un dossier :

:: Write catalog.json, listing the plugin files of the folder
datalab-plugin catalog build \\fileserver\datalab\plugins

:: Check catalog.json against the plugin files of the folder
datalab-plugin catalog check \\fileserver\datalab\plugins

build vérifie les wheels et les modules source sans les exécuter et n’écrit pas l’index si un fichier est refusé. Les wheels conservent leurs vérifications de Python pur, de points d’entrée et de dépendances ; les modules suivent les règles ci-dessous. Les métadonnées administrées, les motifs de retrait et les entrées révoquées sont conservés. Le fichier JSON est remplacé de manière atomique. check signale les fichiers de plugins et de dépendances manquants, modifiés, refusés ou non listés. Relancez build après modification des fichiers à la racine. Les deux commandes renvoient un code de sortie non nul si elles détectent un problème.

Modules en fichier unique dans un catalogue#

Pour un catalogue hors ligne simple, placez le fichier datalab_<nom>.py inchangé à sa racine et ajoutez ce dossier dans Catalogues locaux de plugins. Aucun pyproject.toml, wheel ou accès à Internet n’est nécessaire. Pour générer un index administrable, exécutez datalab-plugin catalog build <dossier>, puis check. Un dossier mixte peut contenir des modules et des wheels :

approved_plugins\
    datalab_spectroscopy.py
    datalab_other_plugin-1.0-py3-none-any.whl
    catalog.json
    dependencies\
        additional_wheel_dependency-1.0-py3-none-any.whl

Le JSON généré utilise kind: "module" et le vrai nom d’importation dans module ; il n’attribue pas de distribution Python fictive au script. Sa version contient filename, une url relative, size, sha256, targets: ["desktop"] et version (éventuellement une chaîne vide). kind est omis ou vaut "wheel" pour les entrées wheel existantes. Ajoutez une contrainte facultative requires_python à une version de module lorsque sa compatibilité est connue.

Un administrateur peut modifier le nom d’affichage, le résumé, la licence et les autres champs descriptifs du JSON, et fournir une identité de catalogue et une version lorsqu’elles ne sont pas accessibles statiquement dans le code source. build conserve ces champs. Une identité ou une version connue dans le code source doit correspondre au catalogue. En présence de métadonnées dynamiques ou de plusieurs classes de plugins, le catalogue décrit le module complet sans l’exécuter. Son identité de catalogue ne réécrit pas le PluginInfo utilisé à l’exécution et n’impose pas de modifier un fichier historique.

Si un module n’a pas de version exploitable, laissez version vide : DataLab compare alors les empreintes SHA-256. La confirmation et la liste des fichiers installés distinguent une version connue d’une révision. Un fichier sans version modifié, ou un contenu différent portant la même version déclarée, demande un accord explicite via Remplacer… ; il n’est pas présenté comme une version plus récente. Les modules déjà installés manuellement par DataLab sont aussi reconnus. Les fichiers des répertoires de développement ne sont pas écrasés ; résolvez un conflit de nom ou retirez la copie non gérée avant d’utiliser l’installation gérée.

Les modules en fichier unique utilisent les paquets déjà disponibles dans DataLab. Leurs instructions import ne sont pas interprétées comme des exigences de paquets, aucune dépendance n’est téléchargée et un sous-dossier dependencies n’est pas installé pour eux. prepare inclut les modules dans le catalogue, mais ne télécharge de dépendances que pour les wheels. Les importations qui ne peuvent pas être vérifiées statiquement peuvent encore échouer au chargement du plugin ; ces erreurs sont alors affichées dans l’onglet Installés.

Pour le catalogue public, publiez le fichier inchangé comme fichier joint nommé d’une release GitHub et indiquez sa version, sa licence, sa description et son SHA-256 dans la fiche YAML. Le code source n’est pas obligé d’exposer ces valeurs statiquement. Une fiche a la structure suivante (remplacez le dépôt, le fichier et l’empreinte d’exemple par les informations de la release réelle) :

id: io.github.alice.spectroscopy
name: Spectroscopy tools
kind: module
summary: A single-file Desktop plugin
license: BSD-3-Clause
repository: https://github.com/alice/spectroscopy
capabilities: [processing]
releases:
  - version: "1.0.0"
    filename: datalab_spectroscopy.py
    sha256: <SHA-256 of the released file>
    requires_python: ">=3.10"

Le catalogue public vérifie le script et le met en miroir dans modules/<sha256>/.... Pour utiliser ce catalogue publié hors ligne, copiez son JSON et toute son arborescence relative, y compris modules et wheels lorsqu’ils sont présents. Ne reconstruisez pas un miroir inchangé dont les fichiers se trouvent dans ces sous-dossiers : les commandes locales de préparation parcourent la racine. Les URL sources, les vérifications de révision, les retraits et la priorité des catalogues locaux suivent les mêmes règles pour les deux formats. Les modules ciblent uniquement Desktop, pas DataLab-Web ni PyPI.

Dépendances supplémentaires et installation hors ligne#

Les plugins Desktop peuvent nécessiter des paquets qui ne sont pas fournis avec DataLab. Conservez le plugin lui-même sous forme de paquet wheel en Python pur et fournissez les paquets supplémentaires, y compris toutes leurs dépendances transitives, sous forme de wheels ordinaires dans un sous-dossier dependencies du catalogue local. Ces paquets de dépendances peuvent contenir des bibliothèques natives, à condition de correspondre à la version de Python, à l’ABI et à la plateforme de l’environnement hôte. Ils n’ont pas besoin de point d’entrée de plugin DataLab.

Sur un ordinateur disposant d’un accès à Internet, la commande de préparation constitue le dépôt de paquets wheel et écrit le catalogue :

datalab-plugin catalog prepare D:\approved_plugins

La commande télécharge les paquets wheel pour l’environnement courant sans les installer ni modifier ses paquets. Elle utilise les dépendances d’exécution déclarées de DataLab comme référence : les plugins sans rapport déjà installés sur l’ordinateur de l’auteur ne sont donc pas confondus avec les paquets livrés avec DataLab. Préparez les paquets dans chaque environnement cible lorsque des versions de Python ou des plateformes différentes nécessitent des fichiers différents, puis copiez le dossier complet sur l’ordinateur hors ligne ou le partage réseau. Les commandes build et check ne téléchargent pas elles-mêmes les paquets manquants.

Par exemple, un catalogue pour CPython 3.11 sous Windows peut contenir :

approved_plugins\
    catalog.json
    datalab_tango-0.1.0-py3-none-any.whl
    dependencies\
        pytango-10.3.1-cp311-cp311-win_amd64.whl
        docstring_parser-0.18.0-py3-none-any.whl

L’onglet Catalogue copie les fichiers de dépendances vérifiés de la version choisie. Pour Installer depuis un fichier…, placez le dossier dependencies à côté du paquet wheel du plugin. DataLab résout l’installation à partir de ces seuls fichiers locaux, sans repli vers un index de paquets et sans compilation. Avant confirmation, il affiche les paquets supplémentaires, leurs versions, leurs tailles, le dossier source et leurs empreintes SHA-256.

Les paquets déjà fournis par l’environnement Python ou par DataLab ne sont jamais remplacés, mis à jour ou rétrogradés. Les paquets supplémentaires sont partagés entre les plugins d’un même environnement d’exécution Python. Une version installée incompatible, un paquet transitif manquant ou un paquet natif non pris en charge entraîne un refus explicite ; aucune installation partielle n’est activée. Les vérifications des métadonnées du catalogue ne remplacent pas cette résolution dans l’environnement hôte réel.

Une installation qui ajoute des dépendances est activée après le redémarrage de DataLab. Un plugin nouvellement installé est alors activé, y compris lorsqu’une liste explicite de plugins autorisés est configurée. Désinstaller le plugin conserve les dépendances partagées. Les environnements Python/ABI/plateforme différents utilisent des répertoires de dépendances séparés ; les dépendances incompatibles avec un environnement hôte modifié sont signalées plutôt que réparées par téléchargement.

Il n’y a pas d’environnement par plugin : des plugins exigeant des versions contradictoires ne peuvent pas coexister. Les paquets nécessitant des bibliothèques système ou des pilotes externes exigent toujours l’installation séparée de ces prérequis. Dans l’application autonome, les dépendances sont destinées à être importées comme bibliothèques ; elles ne fournissent pas d’interpréteur Python externe et le fonctionnement indépendant de leurs scripts en ligne de commande n’est pas garanti. L’installateur Web reste inchangé.

Sous Windows, les chemins des bibliothèques natives doivent également respecter la limite du chargeur de DLL. DataLab utilise des noms courts pour les répertoires de générations et refuse une installation dont les chemins de DLL resteraient trop longs, avant de la publier ; utilisez alors un répertoire de configuration dont le chemin est plus court.

Déploiement hors ligne, pas à pas#

Cette procédure est autonome : l’ordinateur déconnecté n’a besoin ni d’un index de paquets, ni d’un environnement de développement Python, ni d’un accès au site public des plugins. Un partage réseau local, une clé USB ou un simple dossier local convient. Préparer les dépendances manquantes des wheels nécessite un ordinateur de référence connecté ; un catalogue ne contenant que des modules source peut être constitué entièrement hors ligne (voir Modules en fichier unique dans un catalogue).

Important

Un catalogue de plugins est une source de fichiers d’installation, pas un répertoire de recherche de plugins. Ajoutez-le dans Catalogues locaux de plugins, et non dans Répertoires supplémentaires de plugins. DATALAB_PLUGINS_CATALOG indique des catalogues ; DATALAB_PLUGINS indique du code chargé directement. L’installation copie les fichiers approuvés dans le répertoire de configuration DataLab de l’utilisateur : le dossier source ou le partage réseau n’est donc plus nécessaire pour exécuter ensuite le plugin installé.

1. Préparer un catalogue complet sur un ordinateur connecté#

Le fournisseur doit disposer de DataLab installé dans un environnement Python, avec la commande datalab-plugin disponible. L’application autonome ne fournit pas cette commande de préparation ; ses utilisateurs n’ont besoin que des fichiers préparés. Utilisez un environnement de référence correspondant à la version de DataLab, à la version de Python, au système d’exploitation, à l’architecture et aux versions des paquets de l’ordinateur cible. ? > Installation et configuration… permet d’identifier l’installation cible. Un paquet pour CPython 3.11 sous Windows 64 bits n’est pas interchangeable avec un paquet pour Linux, une architecture 32 bits ou CPython 3.12.

Créez un dossier, placez le fichier .whl ou datalab_*.py du plugin à sa racine, puis exécutez :

datalab-plugin catalog prepare D:\approved_plugins
datalab-plugin catalog check D:\approved_plugins

Pour les wheels, prepare résout les exigences manquantes par rapport à l’environnement hôte de référence, télécharge leurs wheels et dépendances transitives dans dependencies, puis écrit catalog.json. La commande ne les installe pas dans l’environnement de référence et ne compile pas de distributions source. Les modules sont inclus sans téléchargement de dépendances. Utilisez build pour un catalogue reposant uniquement sur des fichiers ; si la préparation signale un wheel manquant ou un conflit, corrigez le catalogue avant de le transférer.

Conservez tous les fichiers produits, y compris les paquets de dépendances. Ne copiez pas uniquement catalog.json ou uniquement le paquet wheel du plugin. Pour desservir plusieurs environnements cibles, préparez leurs paquets dans des environnements de référence correspondants, rassemblez les fichiers nécessaires, puis exécutez datalab-plugin catalog build D:\approved_plugins, suivi de check. Un paquet en Python pur peut lui aussi restreindre les versions de Python prises en charge dans ses métadonnées.

check vérifie les fichiers du catalogue, leur intégrité et leurs métadonnées. Cette commande ne remplace pas un essai d’installation sur la cible réelle : la résolution complète des dépendances se fait lors de l’installation. Avant un déploiement plus large, testez le dossier complet sur une installation équivalente dont l’accès à Internet est indisponible.

2. Transférer le dossier en conservant son organisation#

Copiez le dossier complet sur une clé USB, un disque local ou un partage réseau accessible depuis l’ordinateur cible. Conservez les chemins relatifs et les noms de fichiers. Un miroir public peut stocker les fichiers dans wheels\<digest>\... et modules\<digest>\... : conservez aussi ces répertoires, car catalog.json les référence. Le seul fichier JSON n’est pas un miroir et DataLab n’exporte pas automatiquement un catalogue en ligne pour un usage hors ligne.

Pour un catalogue JSON strictement hors ligne, l’URL d’installation (champ url) de chaque version et de chaque fichier de dépendance doit désigner un fichier local existant. Une URL absolue https:// entraîne toujours un téléchargement depuis son serveur, même si le catalogue est local ; placer un paquet wheel à côté de ce JSON ne remplace pas son URL. Les liens informatifs tels que repository, documentation et source_url ne remplacent pas les fichiers d’installation. Les catalogues générés par build utilisent des URL de fichiers relatives ; les miroirs publiés doivent conserver l’arborescence relative correspondante.

L’utilisateur doit disposer d’un accès en lecture à cette source, et d’un accès en écriture à ses propres répertoires de configuration et de fichiers temporaires. Les privilèges d’administrateur ne sont pas nécessaires pour installer un plugin de cette manière. Réservez l’accès en écriture au catalogue partagé à ses responsables ; une vérification SHA-256 détecte les fichiers modifiés, mais ne certifie pas l’innocuité d’un plugin ou d’une dépendance.

3. Configurer l’ordinateur déconnecté#

Ouvrez Plugins > Configurer les plugins… > Avancé. Dans Catalogues locaux de plugins, cliquez sur Ajouter, sélectionnez la racine du catalogue (le dossier contenant catalog.json ou les paquets des plugins), puis appliquez la configuration. Ne sélectionnez pas le sous-dossier dependencies. Ouvrez l’onglet Catalogue et cliquez sur Actualiser si nécessaire.

Les administrateurs peuvent aussi définir la variable d’environnement suivante avant de lancer DataLab :

$env:DATALAB_PLUGINS_CATALOG = 'D:\approved_plugins;\\fileserver\datalab\plugins'

Cet exemple s’applique à DataLab démarré depuis la même fenêtre PowerShell ; un raccourci lancé séparément n’hérite pas de l’environnement de cette fenêtre. Une organisation peut également déployer la variable par son mécanisme habituel de configuration des postes. Les dossiers de la variable d’environnement sont prioritaires sur ceux enregistrés dans les paramètres de DataLab ; les deux sont prioritaires sur le catalogue en ligne. Le premier identifiant de plugin ou nom de distribution correspondant l’emporte : les versions de sources différentes ne sont pas fusionnées.

Avertissement

Ajouter un catalogue local ne désactive pas le catalogue en ligne. Si son URL reste configurée, DataLab tente toujours de le lire lors de l’actualisation, ce qui peut entraîner une attente réseau et une erreur sur un ordinateur déconnecté. Les autres catalogues restent utilisables après cette erreur.

Pour désactiver cette recherche, fermez DataLab, sauvegardez son fichier de configuration et donnez une valeur vide à plugins_catalog_url dans la section [main] existante. Avec le profil utilisateur Windows standard, DataLab 1.3 et les versions suivantes utilisent %USERPROFILE%\.DataLab_v1\DataLab_v1_typed.ini (sous Linux/macOS, normalement ~/.DataLab_v1/DataLab_v1_typed.ini). Les profils personnalisés peuvent utiliser un autre dossier de base. Ne modifiez pas à sa place l’ancien fichier DataLab_v1.ini.

[main]
plugins_catalog_url =

Conservez le reste du fichier. Ne supprimez pas cette option pour la désactiver : une option absente rétablit l’URL publique par défaut. Redémarrez DataLab après modification. Une URL HTTPS privée nécessite toujours un accès à son serveur ; pour une installation hors ligne reposant uniquement sur des fichiers, utilisez un dossier de catalogue local.

4. Installer, confirmer et redémarrer si nécessaire#

Dans l’onglet Catalogue, trouvez le plugin et cliquez sur Installer. DataLab choisit la version la plus récente proposée pour Desktop et pour la version de Python utilisée, vérifie la taille et les empreintes SHA-256 du plugin et des fichiers de dépendances compatibles listés, puis prépare toute installation supplémentaire à partir des seuls fichiers locaux. La sélection d’une version ne garantit pas que toutes ses dépendances puissent être installées : ce point est vérifié dans l’environnement hôte réel avant confirmation.

Lisez la confirmation : elle indique l’identité du plugin, ses classes, ses exigences et son empreinte, ainsi que les paquets supplémentaires, leurs versions, leurs tailles, leurs empreintes et le dossier source si nécessaire. Annuler laisse l’installation inchangée. Après accord, DataLab installe les fichiers dans son stockage utilisateur privé ; il ne modifie pas les versions des paquets de l’environnement et ne recharge pas le code depuis le catalogue partagé à chaque démarrage.

Redémarrez DataLab si des dépendances ont été ajoutées ou si vous remplacez un paquet déjà chargé. Sinon, DataLab peut proposer de recharger les plugins. Après redémarrage, vérifiez l’état du plugin et les éventuelles erreurs d’importation dans l’onglet Installés, puis essayez l’une de ses actions. Le catalogue source peut être déconnecté après une installation réussie. Pour installer un fichier ponctuellement, Depuis un fichier > Installer depuis un fichier… effectue les mêmes vérifications ; conservez dependencies à côté du paquet wheel du plugin.

5. Maintenir et dépanner le catalogue hors ligne#

Lorsque catalog.json existe, il fait autorité : DataLab ne liste et ne copie que les versions et fichiers de dépendances qui y sont déclarés. Pour un catalogue géré à partir de fichiers à sa racine, relancez build et check après ajout ou modification d’un module, d’un wheel de plugin ou de dépendance, puis redistribuez le dossier complet. Copier un nouveau fichier à côté d’un JSON existant ne met pas cet index à jour. prepare peut nécessiter Internet pour les dépendances des wheels ; build et check ne récupèrent jamais les paquets manquants.

N’exécutez pas build sur un miroir inchangé dont les plugins se trouvent uniquement dans wheels\<digest>\... ou modules\<digest>\... : la commande parcourt la racine du catalogue, pas l’arborescence récursive, et supprimerait les entrées non représentées. Mettez à jour un miroir en transférant un catalogue publié complet et cohérent avec ses fichiers. Pour le gérer avec les commandes locales de préparation, disposez d’abord les wheels et modules des plugins à la racine et les paquets supplémentaires dans dependencies.

Les utilisateurs actualisent l’onglet Catalogue pour découvrir les mises à jour, puis cliquent explicitement sur Mettre à jour vers…. Les mises à jour ne sont pas installées automatiquement. Les plugins installés avec pip dans l’environnement Python sont identifiés, mais ne sont pas mis à jour par cette boîte de dialogue. Les dépendances supplémentaires partagées sont conservées lorsqu’un plugin est désinstallé, et leurs versions existantes restent protégées lors des installations suivantes.

Si une installation échoue, lisez l’erreur dans la boîte de dialogue des plugins avant de modifier les fichiers :

  • Catalogue introuvable ou inaccessible : vérifiez la racine sélectionnée, la lettre de lecteur, la clé USB, la connexion réseau et les droits de lecture. Un partage manquant n’est pas un problème d’accès à Internet. Actualisez lorsqu’il est de nouveau disponible.

  • Taille ou SHA-256 incorrect : les fichiers copiés diffèrent du catalogue. Demandez au fournisseur une copie complète et cohérente ou régénérez le catalogue à partir des paquets souhaités ; ne contournez pas cette vérification.

  • Aucun paquet compatible ou exigence manquante : le dépôt peut ne pas contenir une dépendance transitive ou le paquet correspondant à ce Python, à cette ABI ou à cette plateforme. Demandez au fournisseur d’exécuter prepare dans un environnement de référence correspondant. L’installateur ne se replie jamais vers PyPI.

  • Version installée incompatible : l’environnement hôte ou un autre plugin fournit déjà une version de paquet en conflit. Demandez une version ou une installation de référence compatible ; ne forcez pas de mise à jour ou de rétrogradation pour contourner le refus.

  • Chemin de DLL Windows trop long : utilisez un chemin de configuration plus court. Erreur d’importation de DLL ou bibliothèque système manquante : vérifiez les prérequis externes du paquet natif avec le fournisseur ; DataLab n’installe ni pilotes ni paquets système.

  • Installé mais inactif : redémarrez si cela est demandé, vérifiez l’activation globale et individuelle des plugins et consultez l’erreur d’importation affichée dans l’onglet Installés. Un simple rechargement ne remplace pas une bibliothèque native déjà importée.

Pour l’aide locale, utilisez ? > Documentation PDF, puis recherchez Déploiement hors ligne, pas à pas ou DATALAB_PLUGINS_CATALOG. Ce PDF est un fichier local et ne nécessite pas Internet. Documentation en ligne, le lien vers la documentation de la page d’accueil et les liens externes vers le code source ou la documentation ouvrent, eux, des sites web. L’action de menu du PDF n’apparaît que si un PDF local est présent ; DataLab essaie d’abord la langue du système, puis l’anglais. S’il est absent ou illisible, demandez à l’administrateur le PDF livré avec la version correspondante de DataLab plutôt que de dépendre d’un lien en ligne.

Onglet Depuis un fichier#

Cet onglet installe un plugin partagé sous forme de fichier, sans aucun outil Python : c’est ainsi que l’on ajoute des plugins à la version autonome de DataLab. Installer depuis un fichier… accepte deux types de fichiers :

  • un paquet wheel (.whl) construit à partir d’un projet de plugin, par exemple avec python -m build : il doit être en Python pur (py3-none-any), déclarer sa classe de plugin dans le groupe de points d’entrée datalab.plugins, et ses exigences doivent être satisfaites par l’environnement hôte ou le dépôt de dépendances adjacent (voir Dépendances supplémentaires et installation hors ligne) ;

  • un module Python unique nommé datalab_<nom>.py.

Avant l’installation, DataLab vérifie le fichier sans l’exécuter. Pour un wheel, la confirmation affiche la distribution, la version, les points d’entrée et les exigences issus de ses métadonnées. Pour un module en fichier unique, elle affiche son nom d’importation, le fichier, la taille, le SHA-256 et les métadonnées lisibles statiquement ou explicites du catalogue. Une version inconnue reste inconnue et est affichée comme une révision ; aucune liste de classes ou de dépendances n’est devinée. Un plugin s’exécute avec les mêmes droits que DataLab : n’installez que des plugins provenant d’auteurs de confiance.

Les plugins installés sont conservés dans le dossier installed_plugins du répertoire de configuration DataLab (par exemple ~/.DataLab_v1/installed_plugins) et listés dans l’onglet, où Désinstaller les supprime. Les modules peuvent être rechargés après installation ou remplacement ; un plugin nouvellement installé est activé. Les dépendances supplémentaires et les nouvelles versions de wheels déjà chargés ne sont activées qu’au prochain démarrage de DataLab.

Lors du rechargement des plugins, DataLab effectue les étapes suivantes :

  1. Désenregistrer les plugins actuellement actifs et leurs traitements,

  2. Effacer les actions de plugins des panneaux signal et image,

  3. Redécouvrir et recharger les modules de plugins,

  4. Réenregistrer les plugins activés,

  5. Réenregistrer les traitements possédés,

  6. Recréer les actions des plugins et rafraîchir les menus.

Ce flux permet un développement itératif des plugins pendant que DataLab est en cours d’exécution.

Note

L’état d’activation/désactivation des plugins est conservé dans les paramètres de DataLab. Les plugins désactivés restent listés dans la boîte de dialogue de configuration et peuvent être réactivés plus tard. Le réglage global des plugins tiers dans les préférences est lui aussi appliqué immédiatement : le désactiver supprime les actions des plugins et désactive l’indicateur d’état, qui affiche Plugins : -, tandis que le réactiver recharge automatiquement les plugins. L’action du menu Plugins > Configurer les plugins… reste accessible lorsque l’indicateur d’état est désactivé.

Onglet Avancé#

Cet onglet liste tous les répertoires scannés au démarrage, en deux groupes :

  • Répertoires de plugins par défaut (lecture seule) : le répertoire de plugins utilisateur, le dossier datalab/plugins/builtin inclus, le dossier de distribution autonome le cas échéant, et les répertoires déclarés via la variable d’environnement DATALAB_PLUGINS (identifiés par un suffixe (from DATALAB_PLUGINS)).

  • Répertoires de plugins supplémentaires : vos propres répertoires, ajoutés avec le bouton Ajouter et gérés avec les boutons Modifier le répertoire et Supprimer le répertoire. Contrairement à la variable d’environnement, ces répertoires sont enregistrés dans la configuration de DataLab et persistent donc entre les sessions.

Il liste aussi les Catalogues locaux de plugins : des dossiers, éventuellement partagés sur le réseau, dont les plugins sont proposés dans l’onglet Catalogue (voir Catalogues locaux de plugins). Ils se gèrent avec les mêmes boutons, et les dossiers déclarés par la variable d’environnement DATALAB_PLUGINS_CATALOG apparaissent en premier, en lecture seule. Modifier ces dossiers ne nécessite pas de recharger les plugins.

L’onglet contient également une option Avertissements de compatibilité pour masquer les avertissements concernant les plugins DataLab v0.20 incompatibles.

Rechargement à chaud pour le développement de plugins#

La fonctionnalité de rechargement à chaud est conçue pour accélérer le cycle de développement des plugins. Voici le workflow recommandé :

  1. Démarrer DataLab normalement.

  2. Créer ou modifier votre fichier plugin (par exemple datalab_myplugin.py) dans l’un des répertoires de plugins (par exemple ~/.DataLab_v1/plugins).

  3. Dans DataLab, utiliser Plugins > Recharger les plugins pour prendre en compte les modifications instantanément.

  4. Tester les actions du plugin directement dans l’application en cours d’exécution.

  5. Itérer : modifier le fichier, recharger, tester — sans redémarrer DataLab.

Pour activer ou désactiver sélectivement des plugins pendant le développement, utiliser Plugins > Configurer les plugins… et son bouton Appliquer et recharger les plugins, afin que les modifications prennent effet sans quitter la boîte de dialogue.

Aides de l’API plugin#

Les plugins qui héritent de datalab.plugins.PluginBase ont un accès direct à des aides utiles :

  • self.signalpanel et self.imagepanel : accès aux API de panneaux et aux gestionnaires d’actions,

  • self.proxy : une instance de datalab.control.proxy.LocalProxy pour créer des objets et lancer des traitements,

  • show_warning, show_error, show_info, ask_yesno : méthodes pratiques pour les boîtes de dialogue,

  • edit_new_signal_parameters et edit_new_image_parameters : aides pour les boîtes de dialogue de paramètres d’objet.

Ces aides simplifient le code des plugins et le maintiennent cohérent avec le comportement de DataLab.

Les plugins de traitement doivent surcharger register_computations() et enregistrer chaque fonctionnalité avec un feature_id stable de la forme <plugin_id>:<local_id> et owner_plugin_id=self.plugin_id. DataLab appelle cette méthode une fois les panneaux Signal et Image créés. Les fonctionnalités détenues par le plugin sont supprimées automatiquement lorsque celui-ci est désactivé, rechargé ou désinstallé. create_actions() peut ensuite faire référence à la fonctionnalité enregistrée par son identifiant stable.

Une fonctionnalité enregistrée exécute une fonction de calcul Sigima, décorée par sigima.proc.decorator.computation_function(). Pour une fonctionnalité 1 vers 1 sans paramètre, le plus simple est d’envelopper une fonction traitant des tableaux NumPy avec sigima.proc.signal.Wrap1to1Func (valeurs Y d’un signal) ou sigima.proc.image.Wrap1to1Func (données d’une image), comme dans l’exemple de plugin de traitement (voir Exemple : plugin de traitement). DataLab refuse les autres fonctions dès leur enregistrement.

Recettes sans interface graphique#

Les plugins peuvent exposer des workflows scientifiques versionnés via le tuple de classe RECIPES. Chaque datalab.plugins.recipes.RecipeDescriptor déclare un ID stable dans l’espace de noms du plugin, des emplacements d’entrée typés, une classe de paramètres guidata DataSet facultative et une fonction appelable sans interface graphique :

Les descripteurs de recettes restent détenus par la classe de plugin courante et sont lus via datalab.plugins.PluginBase.get_recipes() ; ils ne sont pas copiés dans un registre mutable distinct. Le rechargement de la classe de plugin remplace donc ses déclarations de recettes en même temps que son implémentation.

from datalab.plugins import PluginBase, PluginInfo
from datalab.plugins.recipes import (
  RecipeDescriptor,
  RecipeInputSlot,
  RecipeObjectOutput,
  RecipeOutcome,
)

def run_quick_check(inputs, parameters, context):
  source = inputs["source"][0]
  context.raise_if_cancelled()
  output = source.copy()
  context.report_progress(1.0, "Quick check complete")
  return RecipeOutcome(
    objects=(RecipeObjectOutput("checked-signal", output),),
  )

class MyPlugin(PluginBase):
  PLUGIN_INFO = PluginInfo(
    id="org.example.my-plugin",
    name="My Plugin",
    version="1.0.0",
  )
  RECIPES = (
    RecipeDescriptor(
      recipe_id="org.example.my-plugin:quick-check",
      plugin_version="1.0.0",
      title="Quick check",
      version="1.0.0",
      inputs=(RecipeInputSlot("source", "signal", "one"),),
      run=run_quick_check,
    ),
  )

  def create_actions(self):
    pass

La valeur plugin_version du descripteur doit correspondre à PLUGIN_INFO.version. L’explicitation des versions du plugin et de la recette permet aux traces d’exécution d’identifier à la fois l’implémentation installée et le workflow versionné indépendamment.

DataLab valide les déclarations d’un plugin lors de son chargement : recettes, lanceurs de recettes, exemples, outils et tuiles de la page d’accueil, décrits ci-dessous. Un plugin dont une déclaration est invalide, par exemple une recette dont le plugin_version ne correspond plus à la version du plugin, n’est pas chargé : son erreur est affichée dans la console interne et consignée dans le fichier journal, et le plugin est listé avec cette erreur dans l’onglet Installés de Configurer les plugins… (filtre Plugins avec erreurs). Les autres plugins sont chargés normalement.

La fonction de la recette reçoit une correspondance entre les ID d’emplacements et des tuples d’instances Sigima SignalObj ou ImageObj, l’instance de paramètres DataSet (ou None) et un datalab.plugins.recipes.RecipeExecutionContext. Le contexte fournit des fonctions de rappel de progression et d’annulation indépendantes de la technologie et ne dépend pas de Qt.

Lorsque parameter_class vaut None, la recette ne déclare aucun paramètre et la fonction reçoit None. Dans le cas contraire, les consommateurs doivent fournir une instance de la sous-classe DataSet déclarée. Le runner de recettes applique cette règle avant l’exécution.

Un datalab.plugins.recipes.RecipeOutcome contient des sorties d’objets nommées, des diagnostics structurés et des résultats scalaires facultatifs. Un TableResult ou GeometryResult est encapsulé dans un datalab.plugins.recipes.RecipeResultOutput et utilise anchor_id pour référencer la sortie d’objet nommée qui en sera propriétaire. Le contrat valide ces références sans attribuer d’UUID du workspace DataLab. La mutation du workspace et le commit atomique relèvent du runner de recettes, pas de la fonction de la recette.

Décrire les entrées d’une recette#

DataLab montre aux utilisateurs ce qu’attend chaque recette et si la sélection courante lui convient. Décrivez chaque emplacement d’entrée en conséquence :

from datalab.plugins.recipes import RecipeInputSlot, RecipeMetadataRequirement

FLAT_FRAMES = RecipeInputSlot(
  "flat_frames",
  "image",
  "many",
  title="Flat frames",
  description="Uniformly illuminated frames, two or more per exposure level",
  min_count=4,
  metadata=(
    RecipeMetadataRequirement(
      "org.example.my-plugin.exposure_time_s", "Exposure time in seconds"
    ),
    RecipeMetadataRequirement(
      "org.example.my-plugin.frame_role", "dark or flat", required=False
    ),
  ),
)

min_count est le nombre minimal d’objets affectés à un emplacement many. Les clés de métadonnées requises doivent être présentes sur chaque objet affecté ; les clés facultatives sont des indications montrées à l’utilisateur. L’exécuteur de recettes applique ces deux règles avant d’appeler la fonction de la recette.

Deux points d’extension facultatifs de datalab.plugins.recipes.RecipeDescriptor affinent ces déclarations :

  • suggest_bindings(candidates) renvoie une correspondance entre identifiants d’emplacements et une partie des objets candidats, par exemple pour répartir des images selon leur rôle à partir de leurs métadonnées. Sans lui, les candidats compatibles vont au seul emplacement acceptant leur type, et les emplacements partageant un même type sont laissés à l’affectation de l’utilisateur.

  • check_inputs(inputs, parameters) renvoie une liste de datalab.plugins.recipes.RecipeDiagnostic pour des vérifications rapides propres à la recette, comme les dimensions, les effectifs par niveau ou les unités. Il ne doit pas calculer de résultats. Les diagnostics d’erreur bloquent l’exécution et les avertissements sont affichés avant celle-ci. Une exception levée par ce point d’extension est signalée comme une erreur input-check-failed.

datalab.plugins.recipe_binding.assess_recipe_inputs() combine les déclarations des emplacements et ces deux points d’extension. Elle renvoie un datalab.plugins.recipe_binding.RecipeReadiness comprenant un statut (no_input, needs_assignment, not_ready, warnings ou ready), les affectations proposées, des problèmes structurés que les hôtes traduisent, et les diagnostics de la recette. Le module ne dépend pas de Qt : DataLab-Web utilise donc le même code.

Exécuter une recette sur Desktop#

La plupart des plugins n’appellent pas directement l’exécuteur. datalab.plugins.PluginBase.start_recipe() exécute une recette sur la sélection courante avec le lanceur générique de DataLab. Il évalue la sélection, n’ouvre une boîte de dialogue d’affectation des entrées que si les affectations sont ambiguës ou invalides, édite les paramètres déclarés, puis appelle l’exécuteur. Une action de menu de plugin se résume donc à :

def run_quick_check(self):
  return self.start_recipe("org.example.my-plugin:quick-check")

Les boutons Exécuter… du Panneau Applications utilisent le même lanceur. Un plugin qui a besoin d’une interface dédiée pour une recette peut associer son identifiant de recette au nom d’une méthode du plugin dans la correspondance de classe RECIPE_LAUNCHERS ; le panneau appelle alors cette méthode, sans argument, à la place du lanceur générique.

Utilisez datalab.gui.plugins.recipe_runner.RecipeRunner depuis le thread de l’interface graphique pour exécuter une recette sur des entrées explicites. Il valide les entrées et les paramètres, exécute la fonction sans interface et committe son résultat dans le workspace DataLab :

from datalab.gui.plugins.recipe_runner import RecipeRunner

descriptor = self.get_recipes()[0]
outcome = RecipeRunner(self.main).run(
  descriptor,
  inputs={"source": (source_signal,)},
)

Le runner rejette les emplacements d’entrée manquants, supplémentaires, mal typés ou de cardinalité incorrecte avant d’appeler le code de la recette. Il applique également min_count, les métadonnées requises et les diagnostics d’erreur de check_inputs, valide l’instance DataSet facultative et vérifie l’annulation avant l’exécution, après l’exécution et juste avant le commit. Le code de la recette doit rester sans interface et ne doit pas modifier lui-même le workspace.

Seul un datalab.plugins.recipes.RecipeOutcome validé atteint la phase de commit. Le runner Desktop crée un groupe par panneau de sortie, en utilisant par défaut le titre de la recette, puis ajoute toutes les sorties signal et image. Les ID des résultats scalaires sont conservés sous forme de noms de fonction <recipe-id>:<result-id> sur leurs objets ancres nommés, afin que plusieurs tables ou géométries coexistent sans collision de clés de métadonnées. Un échec pendant l’insertion supprime chaque objet et groupe créé par cette invocation, puis restaure l’état modifié précédent du workspace et le panneau courant.

Provenance locale de l’exécution#

Après une exécution sans interface réussie, le runner Desktop enregistre le même datalab.plugins.recipes.RecipeRunRecord dans les métadonnées de chaque objet de sortie. Son contenu versionné et compatible JSON comprend un UUID d’exécution partagé, les ID et versions du plugin et de la recette, les paramètres résolus au format JSON, les UUID nommés des entrées et sorties, les versions de DataLab et Sigima, le statut terminé ainsi que les horodatages UTC de début et de fin.

Les métadonnées sont conservées lors de l’export JSON et des allers-retours des workspaces HDF5. L’UUID d’exécution partagé relie les sorties entre les panneaux Signal et Image sans ajouter de métadonnées aux groupes ni d’historique global de workflow. Les invocations en échec ou annulées ne committent aucune sortie et ne laissent donc aucune trace d’exécution dans le workspace.

Exemples packagés#

Les plugins peuvent exposer des workspaces DataLab natifs via le tuple de classe EXAMPLES. Chaque datalab.plugins.examples.PluginExample utilise une ressource package:relative/path plutôt qu’un chemin de développement du système de fichiers :

from datalab.plugins.examples import PluginExample

class MyPlugin(PluginBase):
  EXAMPLES = (
    PluginExample(
      id="quickstart",
      title="Quick start",
      description="Small deterministic workspace",
      resource="datalab_my_plugin:examples/quickstart.h5",
      recipe_ids=("org.example.my-plugin:quick-check",),
      expected_checks=("summary-table",),
    ),
  )

  def create_actions(self):
    pass

Le package doit inclure la ressource dans sa wheel. resolve() renvoie un objet traversable importlib.resources qui fonctionne également pour les packages importés depuis une archive ZIP. Pour les API exigeant un chemin du système de fichiers, utilisez as_file() comme gestionnaire de contexte et ne conservez pas le chemin renvoyé après la sortie du contexte.

datalab.plugins.PluginBase.get_examples() valide l’unicité des ID locaux et les références aux recettes. Un plugin enregistré peut appeler open_example("quickstart") pour matérialiser et charger un workspace HDF5 DataLab natif. L’ouverture efface le workspace courant par défaut ; passez reset_all=False pour le fusionner à la place.

recipe_ids liste les recettes pour lesquelles un exemple est conçu. Un exemple peut servir plusieurs recettes, par exemple une rampe d’obscurité analysée par deux méthodes. Un plugin peut aussi générer un exemple en mémoire en surchargeant materialize_example() pour renvoyer un datalab.plugins.examples.PluginExampleData ; sa correspondance parameter_values donne, pour chaque identifiant de recette, les valeurs de paramètres adaptées aux objets générés.

Le Panneau Applications présente chaque recette comme une méthode, avec un statut mis à jour pour la sélection courante et un bouton Exécuter… ; ses détails donnent les entrées attendues et les exemples conçus pour elle. Essayer avec cet exemple appelle datalab.plugins.PluginBase.try_example() : il ouvre l’exemple, préremplit les paramètres de la recette avec les valeurs de l’exemple et exécute la recette une fois qu’ils sont acceptés par l’utilisateur. Les exemples sans recipe_ids sont listés comme jeux de données, qui s’ouvrent seulement.

Outils de plugin#

Une recette couvre une analyse sans interface exécutée par DataLab. Toute autre interaction propre à un plugin d’application, comme un assistant, un éditeur interactif, une étape de préparation des données ou un instrument simulé, est un outil. Déclarez les outils dans le tuple de classe TOOLS de valeurs datalab.plugins.tools.PluginTool :

from datalab.plugins.recipes import RecipeObjectType
from datalab.plugins.tools import PluginTool, ToolSelection

class MyPlugin(PluginBase):
  TOOLS = (
    PluginTool(
      id="annotate",
      title="Annotate frames...",
      launcher="annotate_frames",
      description="Set the acquisition metadata of the selected frames",
      object_type=RecipeObjectType.IMAGE,
      selection=ToolSelection.AT_LEAST_ONE,
    ),
  )

  def annotate_frames(self):
    ...

DataLab liste chaque outil à deux endroits : dans la section Outils du Panneau Applications, et dans le sous-menu du plugin du menu Plugins, après les actions propres au plugin. object_type indique le panneau dont le menu affiche l’outil ; avec None, les deux panneaux l’affichent. selection indique la sélection dont l’outil a besoin : NONE (par défaut), EXACTLY_ONE, AT_LEAST_ONE ou AT_LEAST_TWO objets de type object_type. Lorsque la sélection ne convient pas, DataLab désactive l’entrée de menu et le bouton du panneau Applications, et l’info-bulle du bouton indique quoi sélectionner. icon accepte une ressource package:path, une image module:filename enregistrée auprès de guidata (par exemple datalab:delete.svg) ou un nom de fichier d’icône DataLab ; par défaut, l’outil utilise l’icône du plugin.

Le lanceur est appelé sans argument. datalab.plugins.PluginBase.get_tools() vérifie l’unicité des identifiants locaux et les méthodes des outils, et rejette les outils déclarés par des plugins sans la capacité APPLICATION. datalab.plugins.PluginBase.assess_tool() renvoie la raison pour laquelle un outil ne peut pas être ouvert pour la sélection courante, ou None.

Instruments#

Un outil peut désigner une méthode instrument au lieu d’un launcher. Cette méthode renvoie un datalab.plugins.instruments.PluginInstrument, et DataLab ouvre une fenêtre pour lui : une vue en direct à gauche, les réglages de l’instrument à droite, un bouton En direct qui rafraîchit la vue en continu, une option Nouveau groupe et un bouton Acquérir. Le plugin n’écrit aucun code d’interface utilisateur :

import guidata.dataset as gds
from datalab.plugins.instruments import (
  InstrumentAcquisition,
  InstrumentFrame,
  PluginInstrument,
)

class SourceSettings(gds.DataSet):
  amplitude = gds.FloatItem("Amplitude", default=1.0, unit="V")
  count = gds.IntItem("Signals per acquisition", default=10, min=1)

class Source(PluginInstrument):
  live_interval_ms = 200

  def __init__(self):
    super().__init__(SourceSettings())

  def preview(self):
    signal = self.make_signal()
    return InstrumentFrame([signal], summary="...", value_range=(-2.0, 2.0))

  def acquire(self):
    signals = [self.make_signal() for _ in range(self.settings.count)]
    return InstrumentAcquisition("Source - acquisition 001", signals)

class MyPlugin(PluginBase):
  TOOLS = (
    PluginTool(
      id="source",
      title="Signal source...",
      instrument="signal_source",
      object_type=RecipeObjectType.SIGNAL,
    ),
  )

  def signal_source(self):
    return Source()

DataLab modifie settings sur place, en respectant l’état actif, les groupes et les onglets du DataSet guidata, puis appelle preview() après chaque modification et, en mode direct, toutes les live_interval_ms millisecondes. Un InstrumentFrame contient des signaux tracés ensemble ou une seule image, un court résumé affiché sous la vue, et une plage fixe facultative en Y (signaux) ou de couleurs (image). acquire() renvoie un InstrumentAcquisition : DataLab ajoute ses objets dans un nouveau groupe du panneau correspondant, portant le titre de l’acquisition, et les sélectionne, afin qu’une recette puisse s’exécuter aussitôt sur eux. Les deux méthodes lèvent ValueError avec un message destiné à l’utilisateur lorsque les réglages ne peuvent pas être utilisés ; DataLab affiche ce message dans la fenêtre.

Lorsque l’utilisateur désactive l’option Nouveau groupe de la fenêtre, DataLab ajoute plutôt les objets acquis au groupe courant du panneau : comme ils sont sélectionnés, les acquisitions suivantes vont dans le même groupe, jusqu’à ce que l’utilisateur sélectionne un autre groupe. L’option et le groupe courant sont pris en compte au clic sur Acquérir : les modifier pendant l’acquisition ne change pas sa destination, et un nouveau groupe est créé si le groupe a été supprimé entre-temps. Un nouveau groupe est tout de même créé lorsque le panneau n’a pas de groupe courant, par exemple lorsqu’il est vide. L’attribut de classe new_group définit l’état par défaut de l’option (True par défaut) : un instrument dont les acquisitions sont généralement des objets uniques, comme un attribut d’appareil lu à la demande, peut le mettre à False. Une fois fait, le choix de l’utilisateur est mémorisé pour chaque instrument et prévaut sur cette valeur par défaut.

DataLab crée l’instrument une seule fois par outil et le conserve jusqu’au rechargement des plugins : les réglages sont ainsi conservés d’une ouverture à l’autre.

DataLab Desktop appelle l’instrument en dehors du fil d’exécution de l’interface utilisateur, un appel à la fois, même lorsque sa fenêtre est fermée puis rouverte pendant un appel, et ne modifie ses réglages qu’entre deux appels : un instrument lent, comme un appareil attendant ses données, ne fige pas DataLab. Les méthodes facultatives open() et close() sont appelées à l’ouverture et à la fermeture de la fenêtre, y compris lors du rechargement des plugins ou de la fermeture de DataLab, par exemple pour se connecter à un appareil puis le libérer. Si open lève une erreur, son message reste affiché dans la fenêtre et l’instrument n’est pas appelé : le rafraîchissement ou l’acquisition suivant, par exemple après une modification des réglages, appelle d’abord open à nouveau. close est appelée même si open a échoué, et ne doit libérer que ce qui est encore détenu. Les données reçues par l’instrument dans ses propres fils d’exécution, comme les événements d’un appareil, sont conservées par l’instrument jusqu’à son prochain appel de preview ou acquire.

Les connecteurs d’instruments doivent attacher une entrée de métadonnées experimental_source aux objets acquis avant de les renvoyer ; DataLab ne la remplit pas automatiquement. Utilisez les fonctions make_experimental_source et set_experimental_source de Sigima pour enregistrer, selon le cas, l’adresse de l’appareil, l’attribut, la sélection et les horodatages. Cela identifie l’origine de la mesure, pas une acquisition reproductible. Le guide des données expérimentales de Sigima fournit un exemple et décrit le format portable des métadonnées.

DataLab-Web prend aussi en charge les outils : il les liste aux mêmes endroits, ouvre les instruments dans la même fenêtre et appelle les lanceurs dans l’hôte Pyodide du plugin.

Tuiles de la page d’accueil#

Chaque plugin actif déclarant la capacité APPLICATION ajoute une tuile à la section Applications, en haut de la Page d’accueil. Par défaut, cette tuile est construite à partir du nom, de la description et de l’icône du PluginInfo du plugin. Un clic sur cette tuile affiche la page du plugin dans le Panneau Applications.

L’icône du plugin est déclarée avec PluginInfo.icon, soit sous la forme d’une ressource package:relative/path (image SVG ou bitmap fournie dans la wheel du plugin), soit sous la forme d’une image module:filename enregistrée par un module auprès de guidata (par exemple datalab:delete.svg), soit sous la forme du nom de fichier d’une icône de DataLab. Elle est affichée sur la tuile par défaut, dans le panneau Applications et dans la boîte de dialogue de configuration des plugins ; les plugins sans icône utilisent une icône de plugin générique. Pour proposer d’autres points d’entrée, par exemple pour ouvrir directement un exemple, déclarez le tuple de classe WELCOME_TILES de valeurs datalab.plugins.tiles.WelcomeTile :

from datalab.plugins.tiles import WelcomeTile

class MyPlugin(PluginBase):
  PLUGIN_INFO = PluginInfo(
    id="org.example.my-plugin",
    name="My Plugin",
    icon="datalab_my_plugin:icons/my_plugin.svg",
    capabilities=(PluginCapability.APPLICATION,),
  )
  WELCOME_TILES = (
    WelcomeTile(id="application", title="My Plugin"),
    WelcomeTile(
      id="quickstart",
      title="Open quick start",
      description="Open the packaged quick start workspace",
      icon="datalab_my_plugin:icons/quickstart.svg",
      launcher="open_quickstart",
    ),
  )

  def open_quickstart(self):
    self.launch_example("quickstart")

  def create_actions(self):
    pass

Les tuiles déclarées remplacent la tuile par défaut. La première est la tuile principale du plugin ; les autres sont affichées à côté d’elle lorsque la section Applications a la place nécessaire, et deviennent sinon des actions de son menu, ouvert depuis son bouton « … » ou par un clic droit sur la tuile. Une tuile sans launcher affiche la page du plugin dans le panneau Applications ; sinon, la méthode du plugin indiquée est appelée sans argument. Une tuile sans icon utilise l’icône du plugin. datalab.plugins.PluginBase.get_welcome_tiles() valide l’unicité des ID locaux et les méthodes de lancement, et rejette les tuiles déclarées par des plugins sans la capacité APPLICATION. La page d’accueil actualise ses tuiles lorsque les plugins sont chargés, rechargés ou désactivés, et signale les erreurs levées par une méthode de lancement sans fermer DataLab.

L’utilisateur choisit les applications affichées et leur ordre : la page d’accueil affiche un nombre limité de lignes de tuiles, avec d’abord les applications épinglées, puis celles utilisées récemment, puis les autres par ordre alphabétique (voir Page d’accueil). Un plugin ne peut donc pas compter sur la visibilité de sa tuile : ses fonctionnalités doivent rester accessibles depuis le panneau Applications.

Créer un plugin avec datalab-plugin create#

La commande datalab-plugin est installée avec DataLab sous forme de paquet Python ; la version autonome de DataLab ne la fournit pas. Exécutez-la sans option pour créer un plugin en fichier unique :

datalab-plugin create

La commande demande seulement le nom du plugin et sa description, puis écrit un fichier datalab_<nom>.py dans le répertoire de plugins de l’utilisateur (voir Où est positionné un plugin ?). Sélectionnez Plugins > Recharger les plugins dans DataLab, ou redémarrez DataLab : le plugin ajoute son sous-menu au menu Plugins, avec un traitement d’exemple des signaux sélectionnés. Pour réaliser votre propre traitement, modifiez la fonction sample_processing du fichier, qui reçoit les valeurs Y d’un signal sous forme de tableau NumPy et en renvoie de nouvelles, puis rechargez les plugins.

Des options adaptent le fichier généré :

  • --object-kind image : le traitement d’exemple s’applique aux images, et sa fonction reçoit les données de l’image.

  • --capability : sans la capacité processing, le sous-menu contient une action affichant un message, à remplacer par la vôtre.

  • Un dossier de destination, donné en argument : il doit alors être ajouté aux répertoires de plugins (voir Onglet Avancé).

  • --package et --plugin-id : à défaut, le nom du module et l’ID du plugin sont déduits du nom du plugin. Le nom du module doit commencer par datalab_.

Un fichier existant n’est jamais écrasé. Pour partager le plugin, envoyez son fichier : les autres utilisateurs l’installent avec Plugins > Configurer les plugins… > Depuis un fichier (voir Onglet Depuis un fichier).

Le plugin brut en fichier unique et le wheel peuvent tous deux être publiés dans un catalogue Desktop (voir Modules en fichier unique dans un catalogue). Pour développer un plugin plus important avec le packaging et les tests déjà configurés, créez plutôt un projet structuré en couches avec --project (voir Créer un projet de plugin structuré en couches).

Créer un projet de plugin structuré en couches#

Avec --project, la commande installée datalab-plugin crée un petit projet installable qui respecte les contrats stables des plugins et de propriété des fonctionnalités. Exécutez-la sans autre option pour une configuration interactive :

datalab-plugin create --project

La commande demande le nom d’affichage et le compte GitHub (utilisateur ou organisation) qui hébergera le projet, et propose des valeurs par défaut pour le package Python, l’ID de plugin en notation de domaine inversé, la description et la destination. L’ID de plugin par défaut est io.github.<compte>.<nom> ; les ID org.datalab. sont réservés à l’organisation DataLab-Platform, et org.example. est utilisé lorsqu’aucun compte n’est indiqué. Pour les scripts ou une configuration reproductible, indiquez explicitement les valeurs :

datalab-plugin create --project datalab-camera-characterization \
  --name "Camera Characterization" \
  --github-account DataLab-Platform \
  --package datalab_camera_characterization \
  --plugin-id org.datalab.camera-characterization \
  --description "Characterize scientific cameras" \
  --capability application \
  --capability processing \
  --object-kind image

Le projet généré avec une organisation src applique l’architecture validée par le pilote Camera :

package root (host-independent identity)
├── core
├── workflow
└── adapters
    ├── desktop.py
    └── web.py

core contient le comportement métier indépendant de l’hôte, workflow peut utiliser les contrats de recettes sans interface de DataLab et adapters gère l’intégration aux hôtes. Le point d’entrée datalab.plugins cible l’adaptateur Desktop ; la prise en charge Web démarre explicitement avec le statut unsupported. Un test AST généré empêche core et workflow d’importer des modules d’interface graphique, de navigateur ou d’adaptateur.

Le projet comprend également un datalab.plugins.PluginInfo stable, un traitement d’exemple possédé lorsque la capacité processing est sélectionnée, une configuration Ruff, une documentation de l’architecture et des contributions, un changelog, un README et une licence BSD-3-Clause. La commande refuse d’écraser une destination existante.

Le modèle reste volontairement réduit. Ajoutez des recettes métier, des paramètres DataSet, des exemples empaquetés et une intégration continue spécialisée uniquement lorsque le plugin en a besoin.

Pour essayer le plugin, ajoutez le répertoire généré comme répertoire de plugins (voir Onglet Avancé) et rechargez les plugins : DataLab charge la classe du plugin depuis adapters/desktop.py sans installer le projet. Pour valider le projet, installez-le avec ses dépendances de test et lancez ses vérifications depuis le répertoire généré :

python -m pip install -e ".[test]"
python -m pytest
python -m ruff check .

Le pyproject.toml généré exige Python 3.10 ou ultérieur et la version majeure courante de DataLab (par exemple datalab-platform >= 1.4, < 2), et déclare les URL du projet lorsque le compte GitHub est connu. Le fichier .github/workflows/release.yml généré publie le plugin sans compte PyPI : pousser une étiquette comme v0.1.0 construit le wheel, vérifie que l’étiquette correspond à la version du package, joint le wheel à une release GitHub et affiche la fiche à soumettre au catalogue de plugins DataLab, avec l’empreinte SHA-256 du wheel. Les utilisateurs installent ensuite le wheel avec Plugins > Configurer les plugins… > Depuis un fichier (voir Onglet Depuis un fichier). L’inscription du plugin au catalogue est facultative ; une fois inscrit, il peut aussi être installé depuis l’onglet Catalogue (voir Onglet Catalogue).

Comment développer un plugin ?#

La méthode recommandée pour développer un plugin est de dériver d’un exemple existant et de l’adapter à vos besoins. Vous pouvez explorer le code source dans le dossier datalab/plugins/builtin ou vous référer aux exemples fournis par la communauté.

Note

La plupart des fonctionnalités de traitement des signaux et des images de DataLab ont été externalisées dans une bibliothèque dédiée appelée Sigima (https://sigima.readthedocs.io/fr/latest/). Lors du développement de plugins DataLab, vous importerez et utiliserez généralement de nombreuses fonctions et fonctionnalités de Sigima pour effectuer des tâches de traitement, d’analyse et de visualisation des données. Sigima fournit un ensemble complet d’outils pour la manipulation des données scientifiques qui peut être exploité directement dans vos plugins.

Pour développer dans votre environnement Python habituel (par exemple, avec un IDE comme Spyder), vous pouvez :

  1. Installer DataLab dans votre environnement Python, en utilisant l’une des méthodes suivantes :

    • Paquet Conda

    • Gestionnaire de paquets pip

    • Paquet Wheel

    • Paquet source

  2. Ou ajoutez manuellement le package `datalab` à votre chemin Python :

    • Téléchargez le code source depuis la page PyPI,

    • Décompressez l’archive,

    • Ajoutez le répertoire datalab à votre PYTHONPATH (par exemple, en utilisant le Gestionnaire PYTHONPATH dans Spyder).

Note

Même si vous avez installé datalab dans votre environnement, vous ne pouvez pas exécuter l’application DataLab complète directement depuis un IDE. Vous devez lancer DataLab via la ligne de commande ou en utilisant le raccourci créé par l’installateur pour tester correctement votre plugin.

Exemple : plugin de traitement#

Cet exemple enregistre une fonctionnalité de traitement dotée d’une identité stable et d’un propriétaire, puis crée une action qui l’exécute via le registre du processeur :

# -*- coding: utf-8 -*-

"""
Custom denoising filter plugin
==============================

This is a simple example of a DataLab image processing plugin.

It is part of the DataLab custom function tutorial.

.. note::

    This plugin is not installed by default. To install it, copy this file to
    your DataLab plugins directory (see `DataLab documentation
    <https://datalab-platform.com/en/features/advanced/plugins.html>`_).
"""

import numpy as np
import scipy.ndimage as spi
import sigima.proc.image as sipi

import datalab.plugins


def weighted_average_denoise(data: np.ndarray) -> np.ndarray:
    """Apply a custom denoising filter to an image.

    This filter averages the pixels in a 5x5 neighborhood, but gives less weight
    to pixels that significantly differ from the central pixel.
    """

    def filter_func(values: np.ndarray) -> float:
        """Filter function"""
        central_pixel = values[len(values) // 2]
        differences = np.abs(values - central_pixel)
        weights = np.exp(-differences / np.mean(differences))
        return np.average(values, weights=weights)

    return spi.generic_filter(data, filter_func, size=5)


class CustomFilters(datalab.plugins.PluginBase):
    """DataLab Custom Filters Plugin"""

    FEATURE_ID = "org.datalab.examples.custom-filters:weighted-average-denoise"
    PLUGIN_INFO = datalab.plugins.PluginInfo(
        id="org.datalab.examples.custom-filters",
        name="My custom filters",
        version="1.0.0",
        description="This is an example plugin",
        capabilities=(datalab.plugins.PluginCapability.PROCESSING,),
    )

    def register_computations(self) -> None:
        """Register computations owned by this plugin."""
        wrapped_func = sipi.Wrap1to1Func(weighted_average_denoise)
        self.imagepanel.processor.register_1_to_1(
            wrapped_func,
            "Weighted average denoise",
            feature_id=self.FEATURE_ID,
            owner_plugin_id=self.plugin_id,
        )

    def create_actions(self) -> None:
        """Create actions"""
        acth = self.imagepanel.acthandler
        with acth.new_menu(self.PLUGIN_INFO.name):

"""
Image file formats Plugin for DataLab
-------------------------------------

This plugin is an example of DataLab plugin.
It provides image file formats from cameras, scanners, and other acquisition devices.
"""

import struct

import numpy as np
from sigima.io.base import FormatInfo
from sigima.io.image.base import SingleImageFormatBase

# ==============================================================================
# Thales Pixium FXD file format
# ==============================================================================


class FXDFile:
    """Class implementing Thales Pixium FXD Image file reading feature

    Args:
        fname (str): path to FXD file
        debug (bool): debug mode
    """

    HEADER = "<llllllffl"

    def __init__(self, fname: str = None, debug: bool = False) -> None:
        self.__debug = debug
        self.file_format = None  # long
        self.nbcols = None  # long
        self.nbrows = None  # long
        self.nbframes = None  # long
        self.pixeltype = None  # long
        self.quantlevels = None  # long
        self.maxlevel = None  # float
        self.minlevel = None  # float
        self.comment_length = None  # long
        self.fname = None
        self.data = None
        if fname is not None:
            self.load(fname)

    def __repr__(self) -> str:
        """Return a string representation of the object"""
        info = (
            ("Image width", f"{self.nbcols:d}"),
            ("Image Height", f"{self.nbrows:d}"),
            ("Frame number", f"{self.nbframes:d}"),
            ("File format", f"{self.file_format:d}"),
            ("Pixel type", f"{self.pixeltype:d}"),
            ("Quantlevels", f"{self.quantlevels:d}"),
            ("Min. level", f"{self.minlevel:f}"),
            ("Max. level", f"{self.maxlevel:f}"),
            ("Comment length", f"{self.comment_length:d}"),
        )
        desc_len = max(len(d) for d in list(zip(*info))[0]) + 3
        res = ""
        for description, value in info:
            res += ("{:" + str(desc_len) + "}{}\n").format(description + ": ", value)

        res = object.__repr__(self) + "\n" + res
        return res

    def load(self, fname: str) -> None:
        """Load header and image pixel data

        Args:
            fname (str): path to FXD file
        """
        with open(fname, "rb") as data_file:
            header_s = struct.Struct(self.HEADER)
            record = data_file.read(9 * 4)
            unpacked_rec = header_s.unpack(record)
            (
                self.file_format,
                self.nbcols,
                self.nbrows,
                self.nbframes,
                self.pixeltype,
                self.quantlevels,
                self.maxlevel,
                self.minlevel,
                self.comment_length,
            ) = unpacked_rec
            if self.__debug:
                print(unpacked_rec)
                print(self)
            data_file.seek(128 + self.comment_length)
            if self.pixeltype == 0:
                size, dtype = 4, np.float32
            elif self.pixeltype == 1:
                size, dtype = 2, np.uint16
            elif self.pixeltype == 2:
                size, dtype = 1, np.uint8
            else:
                raise NotImplementedError(f"Unsupported pixel type: {self.pixeltype}")
            block = data_file.read(self.nbrows * self.nbcols * size)
        data = np.frombuffer(block, dtype=dtype)
        self.data = data.reshape(self.nbrows, self.nbcols)


class FXDImageFormat(SingleImageFormatBase):
    """Object representing Thales Pixium (FXD) image file type"""

    FORMAT_INFO = FormatInfo(
        name="Thales Pixium",
        extensions="*.fxd",
        readable=True,
        writeable=False,
    )

    @staticmethod
    def read_data(filename: str) -> np.ndarray:
        """Read data and return it

        Args:
            filename (str): path to FXD file

        Returns:
            np.ndarray: image data
        """
        fxd_file = FXDFile(filename)
        return fxd_file.data

# Dürr NDT XYZ file format
# ==============================================================================


class XYZImageFormat(SingleImageFormatBase):
    """Object representing Dürr NDT XYZ image file type"""

    FORMAT_INFO = FormatInfo(
        name="Dürr NDT",
        extensions="*.xyz",
        readable=True,
        writeable=True,
    )

    @staticmethod
    def read_data(filename: str) -> np.ndarray:
        """Read data and return it

        Args:
            filename (str): path to XYZ file

        Returns:
            np.ndarray: image data
        """
        with open(filename, "rb") as fdesc:
            cols = int(np.fromfile(fdesc, dtype=np.uint16, count=1)[0])
            rows = int(np.fromfile(fdesc, dtype=np.uint16, count=1)[0])
            arr = np.fromfile(fdesc, dtype=np.uint16, count=cols * rows)
            arr = arr.reshape((rows, cols))
        return np.fliplr(arr)

    @staticmethod
    def write_data(filename: str, data: np.ndarray) -> None:
        """Write data to file

        Args:
            filename: File name
            data: Image array data
        """
        data = np.fliplr(data)
        with open(filename, "wb") as fdesc:
            fdesc.write(np.array(data.shape[1], dtype=np.uint16).tobytes())
            fdesc.write(np.array(data.shape[0], dtype=np.uint16).tobytes())
            fdesc.write(data.tobytes())

Plugins et DataLab-Web#

Les plugins sont en grande partie portables entre l’application de bureau et DataLab-Web, l’édition native pour navigateur de la plateforme. La même sous-classe datalab.plugins.PluginBase peut fonctionner dans les deux, car l’API de plugin est partagée. Quelques contraintes s’appliquent toutefois à l’environnement d’exécution du navigateur :

  • Les boîtes de dialogue de paramètres doivent être ouvertes de manière asynchrone. Dans le navigateur, l’appel synchrone param.edit(self.main) ne peut pas bloquer la boucle d’événements ; utilisez plutôt await param.edit_async(self.main). Un plugin écrit de cette façon fonctionne sans modification sur le bureau.

  • Pas d’interfaces graphiques propres à Qt. Les plugins qui intègrent des widgets Qt personnalisés ou s’appuient sur les outils interactifs de PlotPy sont réservés au bureau ; leurs parties graphiques n’ont pas d’équivalent dans le navigateur.

  • L’exécution a lieu dans le navigateur (WebAssembly), sans accès natif au système de fichiers au-delà du système de fichiers en mémoire.

Par conséquent, un plugin qui repose sur une interface graphique personnalisée peut ne pas être entièrement compatible avec DataLab-Web. Le catalogue de plugins DataLab indique lesquels de ses plugins prennent aussi en charge DataLab-Web. Reportez-vous à la documentation de DataLab-Web pour le guide pratique de chargement des plugins dans le navigateur.

Migration de la v0.20 à la v1.0#

Si vous avez des plugins existants écrits pour DataLab v0.20, veuillez consulter le guide de migration pour des instructions détaillées sur la mise à jour de vos plugins pour fonctionner avec DataLab v1.0.

class datalab.plugins.recipes.RecipeRunRecord(run_id: str, plugin_id: str, plugin_version: str, recipe_id: str, recipe_version: str, parameters_json: str, input_uuids: Mapping[str, Sequence[str]], output_uuids: Mapping[str, str], datalab_version: str, sigima_version: str, status: RecipeRunStatus, started_at: str, finished_at: str, schema_version: int = 1)[source]#

L’enregistrement est conservé sous forme de métadonnées JSON (voir to_dict()) dans l’option de métadonnées RECIPE_RUN_RECORD_OPTION de chaque objet de sortie, afin que les consommateurs externes (DataLab-Web, espaces de travail HDF5, outils) puissent s’appuyer sur le schéma suivant (version 1) :

  • run_id (str) : UUID partagé par toutes les sorties d’un même appel de recette

  • plugin_id / plugin_version (str) : plugin propriétaire et sa version

  • recipe_id / recipe_version (str) : recette (<plugin_id>:<name>) et version de son contrat

class datalab.plugins.instruments.PluginInstrument(settings: DataSet)[source]#

Instrument ouvert par un outil de plugin.

DataLab écrit les valeurs modifiées dans settings avant d’appeler preview() ou acquire(). Les deux méthodes lèvent ValueError avec un message destiné à l’utilisateur lorsque les réglages ne peuvent pas être utilisés. Le plugin conserve une instance par outil pendant la session : les réglages sont ainsi conservés d’une ouverture à l’autre.

DataLab appelle open() à l’ouverture de la fenêtre de l’instrument et close() à sa fermeture (y compris lorsque le plugin est rechargé ou que DataLab se ferme). Il appelle ces méthodes, preview() et acquire() une à la fois, en dehors du fil d’exécution de l’interface graphique, même lorsque la fenêtre est fermée puis rouverte pendant un appel, et ne modifie settings qu’entre deux appels : un instrument lent ne fige pas DataLab. Les données reçues par l’instrument dans ses propres fils d’exécution (par exemple les événements d’un appareil) doivent être conservées jusqu’au prochain appel de preview() ou acquire().
